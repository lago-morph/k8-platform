# agent instruction

**Strip server-managed metadata when snapshotting cluster state for cleanup restore.** When a test or script needs to mutate a Kubernetes resource and restore the original via `kubectl apply`, fetch with `kubectl get -o yaml` and strip these read-only fields before saving: `metadata.resourceVersion`, `metadata.uid`, `metadata.creationTimestamp`, `metadata.generation`, `metadata.managedFields`, `metadata.annotations["kubectl.kubernetes.io/last-applied-configuration"]`, and `status`. Without the strip, the cleanup apply hits optimistic-locking ("the object has been modified; please apply your changes to the latest version and try again") and fails.

*Grounded in: 2026-05-28 PR #129 composition-drift restore — first iteration failed on stale `resourceVersion` in the pristine snapshot saved by `kubectl get -o yaml`.*

# justification

PR #129's first attempt at fixing the composition-drift cleanup did the obvious thing: save the live Composition to `/tmp/composition-pristine.yaml` before mutating, apply the mutation, then re-apply the pristine snapshot at cleanup. The chainsaw dispatch came back red with `Error from server (Conflict): the object has been modified; please apply your changes to the latest version and try again`. The pristine snapshot included `metadata.resourceVersion: 1271`, but the mutation step's apply had bumped the cluster's rv to 1272, so the restore's apply hit Kubernetes' standard optimistic-concurrency check. The marginal cost of the strip is a single `yq 'del(.metadata.resourceVersion, ...)'` pipe inserted before the save. The cost of NOT stripping is the 8-minute chainsaw round-trip to discover the conflict plus the iteration to add the strip. The seven fields above (`resourceVersion`, `uid`, `creationTimestamp`, `generation`, `managedFields`, the `last-applied-configuration` annotation, and `status`) are the standard server-managed set; stripping them produces a portable manifest that `kubectl apply` accepts unconditionally regardless of the cluster's current rv.
