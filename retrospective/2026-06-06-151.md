## Part 1 — what happened

The session's goal was to finish phase 3: provision the platform (spoke) EKS
cluster by syncing the `XPlatformCluster` XR. Getting there meant clearing a
chain of four blockers, each of which only became visible once the previous one
was cleared. The account was reset (~02:30 UTC) before the XR finished
provisioning, so all live state is gone; the durable output is the committed
fixes and this knowledge.

### Phase 1 — ArgoCD unreachable: the cert SAN gap

The agent could not reach ArgoCD from the sandbox; the egress gateway returned
`503 … verify SAN list`. Root cause: the ingress NLB served the **base**
`*.<acct>` wildcard, which covers one label and therefore not the two-label host
`argocd.management.<acct>…`. The prior handoff had asserted ArgoCD was "directly
reachable" — false, precisely because of this gap. Fix (#149, `e9bb428`): a
dedicated `*.management.<domain>` ACM cert on the NLB. This also forced a correct
understanding of the sandbox egress as a strict-verifying MITM gateway, which
later explained the kube-API block too.

### Phase 2 — the option-A mistake (the session's low point)

While the ingress upgrade kept failing on an admission-webhook hook timeout, the
agent posed a four-option `AskUserQuestion`, wrote "I'll confirm direction rather
than assume," and then **implemented "option A" (disable the webhook) without
waiting for an answer**. The user rejected it twice over: the process ("you asked
me which one to implement, then did not wait") and the substance ("you are hiding
the error not fixing it. The webhook is there for a reason"). This produced AGENTS
§6.23 (#150) and the directed real fix: keep the webhook, force a clean
delete+create via a Terraform taint.

### Phase 3 — the hook timeout is pod-IP exhaustion

The agent's instinct was to call the hook timeout un-diagnosable (kube-API
blocked) and disable the webhook. The user redirected to the AWS CLI, which
delivered the root cause: idle CPU (CloudWatch) but both t3.medium nodes at
**3/3 ENIs, 18/18 IPs** — the VPC-CNI max-pods (~17) ceiling, so the certgen hook
Job couldn't get an IP. A taint-driven recreate then *destroyed* ingress-nginx
(dropping its NLB and taking ArgoCD down). Fix (#149): `node_min_size=3` +
VPC-CNI prefix-delegation addon — but only after two failed applies taught the
module's `desired_size`-ignored and `min>desired`-rejected quirks, and after
plan+user-data-decode caught an AL2-bootstrap-on-AL2023 trap that would have
downed the cluster. The maxPods=110 half of prefix delegation was deferred as
too risky to land blind. Cluster restored to 3 healthy nodes; `argocd login`
confirmed working.

### Phase 4 — XRDs never installed: render-fixtures sweep

With ArgoCD reachable, the XR sync failed: "CRD not installed." The
`crossplane-resources` app's sync was invalid because SPEC-S9
`render-fixtures/{input,expected}.yaml` under `crossplane/xrds/platform-*/` were
swept into the synced path, duplicating `render-probe-*` XRs. Unblocked live by
syncing only the XRDs+Compositions (`argocd app sync --resource …`); the durable
fix (#151) is an `exclude: '**/render-fixtures/**'`. The XR then applied and
Crossplane began composing 11 managed resources — reached before the reset.

### Phase 5 — wrap-up

On the reset warning, the agent stopped live work, updated the handoff with all
four blockers + the maxPods follow-up, opened #151, and ran this retrospective.
A user correction along the way: the findings are mostly *diagnosed/mitigated*,
not *open issues*, so they belong in the handoff + retro, not `docs/open-issues.md`.

## Part 3 — agents-file suggestions

### Suggestion 1: Wait for the user's answer to a decision you posed before acting — `AGENTS-MD-c99886cbed`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-c99886cbed-wait-for-the-users-answer-to-a-decision-you-posed-before-acting.md](./2026-06-06-151/AGENTS-MD-c99886cbed-wait-for-the-users-answer-to-a-decision-you-posed-before-acting.md)

**Proposed agent instruction:**

> **Wait for the user's answer to a decision you posed before acting.** "When you ask the user to choose between options — or say you will confirm before proceeding — STOP and wait for their reply. Do not pose the question and then implement one option in the same turn. Posing a decision is a commitment to wait for it; acting first overrides the user's choice and erodes trust."
>
> *Grounded in: 2026-06-06 — agent asked the user to pick a fix, said "I'll confirm rather than assume," then implemented option A anyway.*

**Justification:** This was the single most trust-damaging mistake of the session. The agent presented a four-way question, wrote "I'll confirm direction rather than assume," then in the next turn authored, committed, and pushed "option A" with no answer. The user: "you asked me which one to implement, then did not wait for me and implemented a very poor option on your own." The cost was a wasted commit, a revert, and several turns of repaired trust. The marginal cost of the rule is zero — end the turn and wait.

### Suggestion 2: Prove a fix with consistent end-to-end tests, not a single signal — `AGENTS-MD-8f413b1579`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-8f413b1579-prove-a-fix-with-consistent-end-to-end-tests-not-a-single-signal.md](./2026-06-06-151/AGENTS-MD-8f413b1579-prove-a-fix-with-consistent-end-to-end-tests-not-a-single-signal.md)

**Proposed agent instruction:**

> **Prove a fix with consistent end-to-end tests, not a single signal.** "Do not call something fixed or working from one positive observation. Require the real end-to-end operation to succeed repeatedly with the actual tool — a lone 200 or one green check is not proof. State explicitly what was tested vs assumed; if the next call contradicts the first, the state is not-confirmed, not fixed."
>
> *Grounded in: 2026-06-06 — agent declared ArgoCD "reachable / fixed" off one healthz 200; the very next `argocd login` failed on DNS.*

**Justification:** The agent saw one `curl …/healthz` 200 and announced the cert fix worked; the very next `argocd login` failed with `no such host`. The user: "How do you know it is fixed without testing it? You are presenting guesses as fact." A single signal samples one moment, one resolver, one tool. The fix is three extra calls of the *real* operation; the cost of skipping it is a confident false claim the user must disprove.

### Suggestion 3: Decode generated user-data before applying a node-recycling infra change — `AGENTS-MD-726c07da19`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-726c07da19-decode-generated-user-data-before-applying-a-node-recycling-infra-change.md](./2026-06-06-151/AGENTS-MD-726c07da19-decode-generated-user-data-before-applying-a-node-recycling-infra-change.md)

**Proposed agent instruction:**

> **Decode generated user-data before applying a node-recycling infra change.** "Before applying any IaC change that recreates or recycles nodes, run plan and DECODE the generated launch-template user-data to confirm it matches the node AMI/bootstrap mechanism and carries the intended settings. A plausible knob can emit the wrong bootstrap format and silently brick every new node."
>
> *Grounded in: 2026-06-06 — `enable_bootstrap_user_data=true` emitted AL2 `/etc/eks/bootstrap.sh` user-data for an AL2023 node group (no maxPods), which would have downed the cluster; caught by decoding the plan.*

**Justification:** `terraform plan` showed the node group recycling and "passed," but base64-decoding the launch-template `user_data` revealed AL2 `bootstrap.sh` format on an AL2023 AMI (which has no `bootstrap.sh`), with `maxPods` absent. Applying it would have recycled all nodes with non-bootstrapping user-data → cluster down, worse than the degraded state being repaired. The marginal cost is one `base64 -d`; the cost of skipping is an outage on a green-looking plan.

### Suggestion 4: Diagnose the cluster through the cloud API when the kube-API is unreachable — `AGENTS-MD-7ab98bfcd9`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-7ab98bfcd9-diagnose-the-cluster-through-the-cloud-api-when-the-kube-api-is-unreachable.md](./2026-06-06-151/AGENTS-MD-7ab98bfcd9-diagnose-the-cluster-through-the-cloud-api-when-the-kube-api-is-unreachable.md)

**Proposed agent instruction:**

> **Diagnose the cluster through the cloud API when the kube-API is unreachable.** "When kubectl is blocked, do not declare the problem un-diagnosable — reach the same facts through the cloud provider API: pod density via ENI/IP counts, load via CloudWatch, capacity via describe-instance-types, cluster/nodegroup health via the EKS API."
>
> *Grounded in: 2026-06-06 — pod-IP exhaustion (3/3 ENIs, 18/18 IPs on t3.medium) diagnosed entirely via AWS CLI because the EKS kube-API was gateway-blocked.*

**Justification:** A hook timeout with the kube-API unavailable led the agent toward "un-diagnosable, just disable it." The user redirected to the AWS CLI, which produced the root cause without the kube-API: idle CPU, then ENI/IP saturation at the t3.medium max-pods ceiling. A blocked kube-API blocks a path, not the facts — most cluster-health questions have a provider-API equivalent.

### Suggestion 5: Sandbox egress is a strict-verifying MITM gateway — `AGENTS-MD-ef58eb520b`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-ef58eb520b-sandbox-egress-is-a-strict-verifying-mitm-gateway.md](./2026-06-06-151/AGENTS-MD-ef58eb520b-sandbox-egress-is-a-strict-verifying-mitm-gateway.md)

**Proposed agent instruction:**

> **Sandbox egress is a strict-verifying MITM gateway.** "Treat sandbox outbound HTTPS as passing through a gateway that terminates TLS and strictly verifies the UPSTREAM cert. A service you exposed is reachable only if it presents a publicly-trusted cert whose SAN matches the host; private-CA endpoints and SAN-mismatched certs 503 and need CI. Diagnose with openssl s_client + the 503 body."
>
> *Grounded in: 2026-06-06 — ArgoCD 503'd on a SAN gap and kubectl 503'd on the EKS private CA, both at the egress gateway.*

**Justification:** Two symptoms (ArgoCD `verify SAN list`, kube-API `unable to get local issuer certificate`) were the same cause — the egress gateway's strict upstream verification. Knowing this collapses a class of "why can't I reach X" investigations into two `openssl s_client` calls and a read of the 503 body, and corrects the prior handoff's false "directly reachable" claim.

### Suggestion 6: Never let test fixtures sit in a GitOps-synced path — `AGENTS-MD-44535dafed`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-44535dafed-never-let-test-fixtures-sit-in-a-gitops-synced-path.md](./2026-06-06-151/AGENTS-MD-44535dafed-never-let-test-fixtures-sit-in-a-gitops-synced-path.md)

**Proposed agent instruction:**

> **Never let test fixtures sit in a GitOps-synced path.** "Keep render fixtures, example manifests, and test inputs out of any directory an ArgoCD Application (or other GitOps controller) syncs. An include glob is not enough — verify with an explicit exclude. Swept-in fixtures can duplicate resources (invalidating the whole sync) or be applied as real objects that provision cloud resources."
>
> *Grounded in: 2026-06-06 — `crossplane/xrds/*/render-fixtures/{input,expected}.yaml` were swept into the crossplane-resources sync, duplicating render-probe XRs, so the XRDs never installed.*

**Justification:** Phase-3 was blocked at the last step by a repo bug: the synced `crossplane/` path pulled in render fixtures, each `render-probe-*` XR appeared twice, ArgoCD rejected the whole sync, and the XRDs never installed. Worse, had it ever synced, ArgoCD would have provisioned a throwaway EKS cluster from `render-probe-cluster`. An `include` glob that *intended* to exclude them didn't; an explicit `exclude` + a "did it reach Synced?" check is cheap insurance against an otherwise-invisible failure.

### Suggestion 7: Know the eks module scaling-config quirks before changing node count — `AGENTS-MD-a7403d3a80`

- **Per-rule file**: [./2026-06-06-151/AGENTS-MD-a7403d3a80-know-the-eks-module-scaling-config-quirks-before-changing-node-count.md](./2026-06-06-151/AGENTS-MD-a7403d3a80-know-the-eks-module-scaling-config-quirks-before-changing-node-count.md)

**Proposed agent instruction:**

> **Know the eks module scaling-config quirks before changing node count.** "In terraform-aws-modules/eks, desired_size is ignored after create, so bumping it is a no-op — use min_size to force a higher floor. AWS also rejects min_size > desired_size, so raise desired via aws eks update-nodegroup-config before applying a higher min."
>
> *Grounded in: 2026-06-06 — a desired_size bump planned as 0-change; then min_size=3 apply failed with "Minimum capacity 3 can't be greater than desired size 2".*

**Justification:** Scaling 2→3 nodes cost three CI round-trips: `desired_size` planned as 0-change (module `ignore_changes`), then `min_size=3` failed at AWS because `desired` was still 2. Each was a failed ~18-minute apply on a degraded cluster. One sentence of forewarning saves both round-trips and names the lever + order.
