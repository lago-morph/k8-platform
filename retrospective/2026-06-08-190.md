## Part 1 — what happened

### Phase 1 — Burn down the testing-debt list (items 1, 2, 4, 5)

The session's spine was `docs/testing-debt-burndown.md`: an owner-directed, finite
list to clear **before** any new feature work, because the recurring pain was a test
gate you couldn't trust. The work landed as a series of small, independently-reviewable
PRs:

- **Item 1 (gate honesty)** — the eventual-consistency real-AWS asserts in the gating
  chainsaw set were one-shot calls that raced ASM consistency and flaked. The fix
  (originally PR #186) replaced each with a bounded poll that accepts every valid
  terminal state, and widened the XR-Ready bound to 600s. Per owner direction to keep a
  single `main`-vs-#184 line, #186 was **closed** and its fix **folded into #184**; #187
  recorded the clean-build proof and checked off items 1 & 3.
- **Item 2 (excise the nightly lane)** — PR #188 deleted the `CHAINSAW_INCLUDE_REALAWS`
  exclusion, the two never-gating REAL-AWS/NIGHTLY xdatabase scenarios, the unit test that
  *mandated* the lane, and the golden exemption. The RDS behavioral coverage was carried
  forward to the gating live suite (item 4) rather than left in a lane nobody blocks on.
- **Item 4 (the capstone — make the live suite actually gate, fail-closed)** — PR #190,
  on the **scope-and-grow** model the owner approved. A dedicated `workflow_dispatch`
  producer (`live-verify.yml` → `live-verify-run.sh`) runs `tests/live/run.sh` under the
  scoped verifier/reaper role and emits an unforgeable `live-evidence` artifact; a
  fail-closed gate (`live-evidence-verify.yml` + `live-evidence-gate.sh`) RED-s any config
  reconciled without fresh evidence keyed on `(sha × account × cluster × profile)`. A
  spike caught a latent trust bug (the trust required a `live-verify` session tag but
  didn't grant `sts:TagSession`, so the tagged assume-role failed `AccessDenied`). The
  gate was proven RED-on-no-evidence and GREEN-on-real-evidence; one real behavioral check
  (RDS Instance) ships, with the registry tracking the remaining ~13 kinds `pending:P*`.
- **Item 5 (infra hygiene)** — PR #189 added a fail-closed ADR-number collision lint +
  `next-adr-number.sh`, and a non-blocking session-start `git fetch origin main` + behind-`main`
  warning to attack the stale-clone root cause.

All five burndown items are now addressed and #187–#190 are merged to `main`
(`ffd5d7d`). The gate is trustworthy: red means real, no nightly.

### Phase 2 — Consultation: designing the next-session prompts and the unattended run

The tail of the session was advisory, not code: the owner asked for prompts to drive the
*next* work — authoring the 13 deferred per-kind behavioral checks (Track A) and continuing
FINAL-PLAN P3–P5 (Track B) — first as two parallel agent sessions, then re-scoped to an
**unattended** "fire-and-sleep" run. The key design conclusion: with one shared live
hub/spoke and the account-mutex (the thing that would make parallel-live safe) itself
unbuilt P3 work, the only safe fire-and-sleep structure is **one sequential autonomous run**
that parallelizes authoring via subagents but serializes every live-cluster operation. The
owner acted on this — the unattended run **auto-014** (#191 scope envelope, #192 sandbox
tool bootstrap) is now in flight from a separate session.

### Phase 3 — The stale-clone mishap (the session's sharpest lesson)

While reconciling state at the end, the local `origin/main` was discovered to be frozen at
`b3efd16` (container-clone time) while real `main` had advanced to `ffd5d7d` with #189 and
#190 merged. This stale view is why earlier turns reported #189/#190 merge state
inconsistently and re-asked an already-answered merge question. The irony is sharp: **#189,
authored *this* session, exists specifically to warn about stale clones** — but its warning
is non-blocking and fires at session start, so it didn't prevent mid-session reporting from
stale refs. A single `git fetch` resolved it and confirmed the burndown was genuinely
complete and merged.

## Part 3 — agents-file suggestions

### Suggestion 1: Verify PR and merge state from the remote, never from stale local refs — `AGENTS-MD-40875d4ee8`

- **Per-rule file**: [./2026-06-08-190/AGENTS-MD-40875d4ee8-verify-pr-state-not-stale-refs.md](./2026-06-08-190/AGENTS-MD-40875d4ee8-verify-pr-state-not-stale-refs.md)

**Proposed agent instruction:**

> **Verify PR and merge state from the remote, never from stale local refs.** "Before asserting that a PR is merged/open or that a branch is on `main`, run `git fetch origin main` (or query the GitHub API). The sandbox clones once at container start; local `origin/main` is frozen at that moment and silently drifts behind. Never report merge state, re-ask a merge decision, or rebase off a local ref without fetching first."
>
> *Grounded in: this session reported #189/#190 merge state inconsistently and re-asked an already-answered merge question because local `origin/main` was pinned at `b3efd16` while real `main` had advanced to `ffd5d7d`.*

**Justification:**

This bit hard and visibly: the agent re-asked the owner a merge question that had already
been answered and acted on, and wavered on whether #189/#190 were merged — all because the
local `origin/main` ref was hours stale. The repo *already* added a session-start fetch-and-warn
this very session (#189), proving the team agrees the stale clone is a real hazard; the gap
is that the warning is non-blocking and one-shot, so mid-session state assertions still read
frozen refs. The marginal cost of the rule is one `git fetch origin main` (sub-second) before
any merge-state claim. The cost of *not* having it is user-visible confusion and wasted
round-trips — exactly what happened. The asymmetry is overwhelming.

### Suggestion 2: Run unattended sessions that contend on a singleton live resource sequentially — `AGENTS-MD-3a981a7295`

- **Per-rule file**: [./2026-06-08-190/AGENTS-MD-3a981a7295-sequential-unattended-on-singleton.md](./2026-06-08-190/AGENTS-MD-3a981a7295-sequential-unattended-on-singleton.md)

**Proposed agent instruction:**

> **Run unattended sessions that contend on a singleton live resource sequentially.** "Do not fan an unattended run into multiple parallel agent sessions when they would contend on a single shared live resource (one cluster, one account, one hub). Parallelize only the work that is genuinely isolated (file authoring, static checks); serialize every operation that drives the singleton. If the mechanism that would make parallel-live safe (an account-mutex) is itself unbuilt, the run is sequential by definition."
>
> *Grounded in: the unattended-run design at this session's tail — one live hub/spoke and an as-yet-unbuilt account-mutex forced a single sequential run rather than two parallel agents.*

**Justification:**

The owner explicitly wanted "fire two and go to sleep" parallelism for speed. The honest
answer was that two unattended agents driving one hub/spoke would clobber each other's live
evidence and let the reaper friendly-fire — and the account-mutex that would fix this is
itself unbuilt P3 work, a chicken-and-egg. Encoding the rule prevents a future session from
optimistically fanning out an unattended run and corrupting live state while nobody is
watching. The marginal cost is near zero (it only constrains the *live* operations; authoring
still parallelizes via subagents). The cost of getting it wrong is a silently-corrupted
overnight run discovered in the morning. This is a load-bearing safety constraint for any
delegated execution against shared infra.
