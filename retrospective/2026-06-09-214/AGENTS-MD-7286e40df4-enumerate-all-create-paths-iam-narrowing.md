# agent instruction

**Enumerate and exercise all create paths for resource-scoped IAM narrowings.** When narrowing a resource-scoped IAM action (such as `iam:GetRole`) for a Crossplane provider role, enumerate every create path that the target service invokes and exercise each one on a fresh-account bring-up before declaring the narrowing validated. Explicitly allow AWS service-linked-role paths (`role/aws-service-role/*`) for any service (EKS, RDS, etc.) that validates service-linked roles at create time. A narrowing validated on one create path (e.g. spoke-access entry creation) is NOT validated for other paths (e.g. nodegroup creation) — each path must be independently proven. If any create path cannot be exercised in the current session, document it in `docs/open-issues.md` and do not mark the narrowing complete.

*Grounded in: auto-016 — auto-015 narrowed `iam:GetRole` to `role/k8-platform-*` and validated only the spoke-ACCESS path; the narrowing silently broke EKS `CreateNodegroup` (which validates `AWSServiceRoleForAmazonEKSNodegroup` via `iam:GetRole` on `role/aws-service-role/eks-nodegroup*`), causing the spoke to come up with 0 nodes on a fresh-account bring-up.*

# justification

auto-015 narrowed `iam:GetRole` to `Resource: arn:aws:iam::*:role/k8-platform-*` and validated it by proving the spoke-ACCESS create path (OIDC provider, Roles, RolePolicy, AccessEntries, AccessPolicyAssociations all `Ready=True`). That was one create path out of at least two: the other is EKS nodegroup creation, where AWS internally calls `iam:GetRole` on the AWS-owned service-linked role `AWSServiceRoleForAmazonEKSNodegroup` (path `role/aws-service-role/eks-nodegroup.amazonaws.com/*`). The narrowing excluded that path. On a fresh-account bring-up in auto-016, where the narrowed policy applied from the start, nodegroup creation failed closed — the spoke came up with **zero nodes**, and the entire app stack stalled. auto-015 never caught this because its nodegroup was created *before* the narrowing was applied.

The cost of not having this rule: a regression that is invisible on the session that ships the narrowing (because that session's nodegroup already exists), invisible in CI static lints (they check actions, not runtime service-linked-role paths), and only surfaces on the *next* fresh-account bring-up — potentially a full unattended run later. In auto-016, diagnosing and fixing it burned roughly an hour of unattended run time and a live patch. The fix (PR #213) was a one-line Sid addition to `irsa.tf`; the detection cost was a zero-node spoke and a full diagnostic sequence.

The marginal cost of adopting this rule: before declaring any resource-scoped IAM narrowing complete, spend 5–10 minutes listing the AWS API calls the controlled service makes at create time (EKS nodegroup creation → validates SLR; RDS instance creation → validates SLR; ACM cert provisioning → different path). One extra `aws iam simulate-principal-policy` per path (noting §6.39's limitation — use as a pre-flight only, not a substitute for a live create-path proof). The asymmetry is severe: the rule adds minutes of due diligence; the absence of it adds hours of fresh-account debugging.
