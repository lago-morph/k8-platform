## Part 1 — what happened

### Phase 1 — Read the user's intent, then read the repo

The user's opening message described a problem ("the workflow is not granular enough — I want to apply phase by phase, then iterate destroy/apply on the active phase only") and asked for a *plan*, not implementation. The starting context was two summary docs the user had pre-pointed to: `summary/functionality-2026-05-17.md` (657 lines) and `summary/status-2026-05-17.md` (354 lines). Both were read in full first, then `.github/workflows/terraform-test.yml`, `.github/scripts/post-comment.py`, `.claude/skills/terraform-ci-watch/SKILL.md`, and `ai/handoff.md`. That base of context proved sufficient for the whole planning sequence — no further reads were needed before drafting the first plan.

### Phase 2 — First plan: structural but missing the doctrine

The initial plan presented:

1. Two `workflow_dispatch` inputs (`phase` × `action`) replacing `mode`.
2. Step-by-step `if:` gating for each combination.
3. Concurrency change (`cancel-in-progress: false`).
4. Updates to `post-comment.py`, `terraform-ci-watch`, `CLAUDE.md`, `ai/handoff.md`, `docs/operations.md`.
5. Commit sequence of 5 small PRs.

It was structurally complete but treated the doctrine ("here's how the agent should *think* about phases") as edits-to-existing-docs rather than as a brand-new conceptual layer. The user immediately challenged this in two ways:

- "Is there a workflow baked in anywhere right now? Instructions to an agent about how to go about bringing up different phases, then the idea to iterate on the current phase without burning down the rest? I don't see it anywhere."
- "If we make it explicit it will be easier for the agent to do it the way I want."

Both observations were correct. A grep across `CLAUDE.md`, `ai/`, `docs/`, `README.md`, and `.claude/skills/` confirmed: zero mentions anywhere of per-phase apply/destroy, of iterating phase N without touching phases 0..N-1, or of "no end-of-session destroy needed because the sandbox expires." The only documented loop was the monolithic `apply-and-destroy`. The plan needed to be re-ordered: **doctrine first, mechanics second**, and the doctrine had to be a substantial new doc, not an addendum.

### Phase 3 — Refined plan: doctrine-first, with the "work on phase N" trigger

The user's follow-up message added the trigger pattern: a single conversational phrase ("work on phase N") that the agent expands into the full procedure — cumulative bring-up of phases 0..N-1, drop into the debug loop for phase N. They also asked for the agent to **author uncoded phases from `ai/REQUIREMENTS.md` + `ai/DESIGN.md` in parallel with the CI bring-up** of earlier phases, joining the two threads once phase N-1 reports verified. That parallelism insight changed the cost equation: a not-coded-phase-N session is no longer "wait 18 minutes for bring-up, then code, then wait 15 more minutes for apply" — it's "code-during-bring-up, push immediately when ready, the two threads converge."

The refined plan introduced:

- A **6-state phase model** (`not-coded`, `code-only`, `plan-green`, `applied`, `verified`, `broken`) — explicit enough that an agent can decide what to do next from state alone.
- A **"Work on Phase N" procedure** in `ai/testing-guidelines.md` §3 that the agent runs end-to-end without further prompting.
- An **inner debug loop** scoped to phase N with three invariants: never destroy below N, never destroy at session end, update handoff after every state change.
- A **`Current Sandbox Session` block** at the top of `ai/handoff.md` that holds per-session state (sandbox start, estimated expiry, per-phase states with last action + run URL). This is separate from the existing `Iteration progress` table, which holds cumulative project state.

The user approved the refined plan with "go forward."

## Part 4 — proposed ADRs

Architectural decisions made or codified in this session that you may want to record formally. **Titles only — no specs.** Use the `adr` skill to author any of these if you decide they're worth recording.

- **Phase development workflow: granular per-phase actions instead of monolithic apply-and-destroy.** Establishes that every phase has its own apply/verify/destroy lifecycle in CI, and that "work on phase N" is the agent's primary control surface. Codifies the three invariants (no destroying lower phases, no end-of-session destroy, update handoff after every state change).

- **`ai/handoff.md` is split into per-session state and cumulative project state.** The new "Current Sandbox Session" block tracks what's live *right now* in the active AWS account; the existing "Iteration progress" table tracks what has *ever* been verified across the project's history. Two tables, two questions, two cadences of update.

- **End-of-session `terraform destroy` is forbidden.** The Pluralsight sandbox auto-expires after 4 hours and reclaims everything; running destroy at session end is wasted budget and risks leaving partial state. `destroy` exists only for the inner debug loop on the active phase.
