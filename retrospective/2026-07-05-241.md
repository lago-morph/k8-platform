## Part 1 — what happened

### Phase 2 — the Keycloak design explainer, and two terminology corrections from the owner

Asked to explain the Keycloak design in plain language (broker, not user store; federate EKS auth so cluster access is a directory-group property rather than an AWS-principal one), I made two errors the owner caught:

1. I called an AWS Secrets Manager secret a **"container"** — a word that collides head-on with the Kubernetes/pod meaning in a k8s conversation. The owner: "What container? Do you mean a container in a pod?" The `human-scoped-deliverables` skill already forbids exactly this (vocabulary discipline / corpus terms); I violated it. Corrected to "the AWS Secrets Manager secret the Composition created."
2. More substantively, the owner interrogated retro-236 Proposal 4 (revert-verification) with "how could anything be left behind if you reverted commits? Git doesn't leave things behind accidentally." This was correct and it dismantled the proposal — see Phase 3.

### Phase 3 — the mishap: a proposed remedy was circular, and owner review is what caught it

Retro-236 Proposal 4 said: after a multi-commit revert, diff the tree against "the last pre-feature commit" to catch leftovers. The owner's push exposed the circularity: *choosing the pre-feature baseline requires knowing the feature's exact commit extent — the very knowledge whose absence caused the bug.* If I'd had it, I wouldn't have botched the revert.

Investigating the actual failure (the #231 admin-secret bug) sharpened the root cause well past "wrong commit set." The admin-secret file was touched by **two** commits on the PR-227 branch: the material-chain commit (in the revert set) and a *separate* commit titled "explicit ESO remoteRef defaults + 5m refresh on the DB legs" (NOT in the revert set) that added three lines *inside the same block*. `git revert` subtracts a named commit's patch; it does not restore content. With an out-of-set commit having also written the file, reverting the named set could never return it to baseline. The failure was a **partial revert of interleaved commits**, and there was no single clean pre-feature commit for that file to diff against — the owner's instinct was exactly right.

The honest resolution: **retire Proposal 4, don't patch it.** The genuinely new content was zero — the baseline-diff version is circular, and the only non-circular version ("review every file touched anywhere in the branch range") collapses into existing diff-review discipline. The real safeguard is the per-file content-invariant test, which is already policy and was already in place for the file that broke (the #231 self-flagging quarantine test). This is the most valuable item in this retro: a proposed safeguard must be checked against *whether it could have fired given the failure's information state.*

### Phase 4 — implementing the four sandbox-completable guards (PR #241)

With Proposal 4 retired, the remaining four remedies were all sandbox-completable and independent, shipped as one reviewable PR (five commits):

- **SUBSTRATE rows 9/10/11** — phase-5 identity gap made explicit (row 9 keycloak-boots DONE 1×; rows 10/11 pending blockers).
- **placeholder lint** — `TODO_` in any runtime value = defect; `PLACEHOLDER_` must be one of four inert-by-override tokens. Scans string leaf values via yq, so the realm header documenting the failure mode is invisible to it (comments aren't values). Red-first fixture; green on the tree.
- **`--output text` boolean lint** — per-file dataflow taint: a var captured from an `aws --output text` substitution is tainted unless the capture normalizes case; a tainted var compared case-sensitively to `true`/`false` is the bug. Catches the pre-#235 form, clears on the `tr` fix.
- **dispatch-SHA guard** — the pre-chainsaw hook now recognizes the `mcp__github__actions_run_trigger` transport (not just the jentic execute path — the hook would never have fired on the transport that actually caused the bug) and blocks any `commit_sha` that isn't a full 40-hex SHA resolving to a real commit. Pure-local, so the blocking hook stays fast and the test stays hermetic.

Each lint carried a red-first fixture and landed green tree-wide (audit-before-enforce). One local-suite red during the work was the resumed sandbox's dead dockerd, re-confirming the existing "read the failure before theorizing" discipline (composition-render needs the daemon; the account-id lint separately flagged a bare account number I'd added, fixed by dropping it).

## Part 3 — remedy proposals (classified per `ai/LESSONS.md` §3)

### Proposal 1 — vet a proposed safeguard against the failure's information state — class (b) judgment / retro-process rule (owner decision)

The Proposal-4 mishap generalizes: **a proposed safeguard is worthless if firing it requires knowledge the failure itself denied you.** Proposal 4 asked to diff against a baseline whose selection needed the commit-extent knowledge whose absence *was* the bug. Candidate one-liner for the self-retrospective skill's anti-patterns (or LESSONS): *"Before proposing a safeguard, confirm it could have fired at the moment of the failure with only the information then available; a check that presupposes the missing knowledge is circular — prefer a content-invariant test that asserts the intended end-state regardless of how it was reached."* This is the highest-value item here; it is a method for the retro process itself, so it belongs in the skill/LESSONS, not in code.

### Proposal 2 — record the partial-revert tooling fact — class (a) documentation (`ai/environment.md`)

`git revert {A,B,C}` subtracts those commits' patches; it does **not** restore content when an out-of-set commit also touched a file. A partial revert of an interleaved branch will silently leave that file off-baseline (the #231 root cause). Proposed `ai/environment.md` tooling line: *"To put a file back to a known-good state, set its content explicitly (`git checkout <good-ref> -- <file>`) or assert it with a test — never reverse-patch a subset of a branch's commits and trust the result; a commit outside the revert set that touched the same file leaves it off-baseline."* Class (a) — an environment fact that bit, adjacent to the existing AWS/tooling facts section.

### Observations (class d, no action)

- **The dispatch-SHA guard's first draft only covered one transport.** The original hook filtered on the jentic `mcp__*__execute` path, but the hallucinated-SHA bug happened on `mcp__github__actions_run_trigger`. A guard that doesn't cover the path the capability is actually exercised through is a guard in name only — this is L8 ("scan every path where the bug class can occur") applied to hooks, already a lesson; noting the recurrence, not a new rule.
- **Owner review caught what unit tests could not.** Proposal 4 would have passed any test — it was a plausible-sounding rule with no code. The filter that killed it was a human asking "how would that even work?" Worth remembering when a remedy is prose rather than a check.
- **A human-facing deliverable violated an existing skill.** The "container" overload is precisely what `human-scoped-deliverables` (vocabulary discipline) exists to prevent; the skill was loaded and I still did it. The skill is correct; the lapse was mine.
