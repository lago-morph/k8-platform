## Part 3 — agents-file suggestions

### Suggestion 1: Select by the crossplane-kind tag, never by name — `AGENTS-MD-8fe3370561`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-8fe3370561-select-by-crossplane-kind-tag.md](./2026-06-08-199/AGENTS-MD-8fe3370561-select-by-crossplane-kind-tag.md)

**Proposed agent instruction:**
> **Select Crossplane-built cloud resources by the provider crossplane-kind tag, never by name.** "When a live check must find the real cloud resource a Crossplane abstraction produced, select it by the provider-stamped tag `crossplane-kind=<kind>.<group>` (plus `PlatformAbstraction`), never by resource name. The Upbound provider auto-generates names (an XDatabase RDS instance is named `terraform-<rand>`), so a name match both misses the real resource and can match a Terraform lookalike."
>
> *Grounded in: auto-014 Track A, where the live XDatabase RDS was named `terraform-...` yet tagged `crossplane-kind=instance.rds.aws.m.upbound.io`.*

**Justification:** Every behavioral oracle must distinguish "Crossplane produced this" from a Terraform/manual lookalike. The provider sets the cloud name itself when no external-name is pinned — producing `terraform-<rand>` for a Crossplane RDS — so name-matching yields false SKIPs (→ false RED via expect-full) and false PASSes. `crossplane-kind` is exact and a Terraform resource never carries it. Cost: one `list-tags` per candidate. Cost of ignoring: a whole class of silently-wrong oracles.

### Suggestion 2: A leftover/value-less artifact SKIPs, not FAILs — `AGENTS-MD-a543251eaf`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-a543251eaf-leftover-artifact-skips-not-fails.md](./2026-06-08-199/AGENTS-MD-a543251eaf-leftover-artifact-skips-not-fails.md)

**Proposed agent instruction:**
> **A leaked or value-less test artifact must SKIP, not FAIL, in a live suite.** "When a behavioral check finds a Crossplane-stamped resource that is empty/value-less or a known test leftover (e.g. an ASM secret with no AWSCURRENT version), treat it as SKIP (not-a-healthy-product), not a hard FAIL. A single FAIL turns the whole suite RED; the orchestrator still promotes the SKIP to a FAIL where the kind is expect-full, and the instantiate tier is the rigorous create-and-verify gate."
>
> *Grounded in: auto-014, where a chainsaw-leftover ASM secret made the secretsmanager check exit 1 and turned the whole after-tier RED.*

**Justification:** A live suite must go RED only for a real regression. A value-less/mid-provisioning artifact is indistinguishable from "not really provisioned"; hard-FAILing makes the gate cry wolf. The inverted-skip orchestrator still promotes a SKIP to FAIL for any expect-full kind, and the instantiate tier verifies a real valued resource — so the gate is not weakened. Marginal cost: one branch. Cost of getting it wrong: a permanently-distrusted suite.

### Suggestion 3: expect-full only CI-runnable kinds — `AGENTS-MD-bb0bf9a697`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-bb0bf9a697-expect-full-only-ci-runnable-kinds.md](./2026-06-08-199/AGENTS-MD-bb0bf9a697-expect-full-only-ci-runnable-kinds.md)

**Proposed agent instruction:**
> **Broaden a scope-and-grow expect-full set only to kinds runnable under the scoped CI identity, not merely provisioned.** "Before adding a kind to a CI gate's expect-full set, confirm its check passes under the actual CI identity/runner, not just from an admin sandbox: relay/kubectl-based checks SKIP on a runner without those tools, and AWS-describe checks SKIP if the scoped role lacks a read verb. A kind that is provisioned but not CI-runnable would wrongly turn the gate RED."
>
> *Grounded in: auto-014, where SecurityGroupRule + ExternalSecret pass from the sandbox but SKIP on the runner, and the acm/iam checks needed three scoped read verbs.*

**Justification:** "Provisioned and healthy" is necessary but not sufficient — the gate runs under a restricted identity on a specific runner. Two traps in one run: relay/kubectl checks pass from the sandbox but SKIP on a kubectl-less runner; AWS-describe checks SKIP until the scoped role's verbs are added and applied. Either silently flips the producer RED after a "harmless" broadening. Cost: one verification under real CI conditions. Cost of skipping: a gate that blocks every PR.

### Suggestion 4: Assume the scoped role to diagnose its perms — `AGENTS-MD-ad9d969ab7`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-ad9d969ab7-assume-scoped-role-to-diagnose-perms.md](./2026-06-08-199/AGENTS-MD-ad9d969ab7-assume-scoped-role-to-diagnose-perms.md)

**Proposed agent instruction:**
> **Diagnose a scoped role's exact permission gaps by assuming it from the sandbox before editing its policy.** "When a scoped role may lack permissions, `aws sts assume-role` into it from the sandbox (with any required session tag) and run the real calls to see exactly which are denied, rather than guessing verbs to add. Confirm the additions are both necessary and sufficient by elimination."
>
> *Grounded in: auto-014, where assuming the verifier/reaper role surfaced exactly three DENIED verbs while every other call was already allowed.*

**Justification:** Guessing IAM verbs over-grants (defeating zero-wildcard) or under-grants (the next run still fails). Becoming the role and running the real calls turns a hand-wave into a precise, provably necessary-and-sufficient diff. Cost: one assume-role. Payoff: a minimal, correct, first-try policy change instead of a guess-and-recheck loop through CI.

### Suggestion 5: No self-gating SKIP stub — `AGENTS-MD-85faaef957`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-85faaef957-no-self-gating-skip-stub.md](./2026-06-08-199/AGENTS-MD-85faaef957-no-self-gating-skip-stub.md)

**Proposed agent instruction:**
> **Never pre-stage a self-gating SKIP-until-reachable stub for deferred coverage.** "Deferring a behavioral check by committing a stub that SKIPs until some precondition is met re-introduces the silent-skip-reads-green disease: an all-skipped-RED floor is suite-level, and a non-COVERS SKIP never triggers expect-full promotion, so the stub rots green for months. Defer with an open-issue entry instead; ship the check as a HARD gate when the precondition is met."
>
> *Grounded in: auto-014 decision brief auto-014-003, where a reviewer showed a self-gating hub-to-spoke curl stub would SKIP undetected.*

**Justification:** A self-gating stub feels responsible but is the exact failure ADR-0006 kills. Verified against the orchestrator: the all-skipped floor is suite-level and a no-COVERS SKIP never enters expect-full promotion, so one stub SKIPs silently forever while the suite reads green. A deferred gap belongs in `docs/open-issues.md` (a human reviews it) plus a plan to ship a HARD check. Cost: an OI entry. Cost of the stub: months of fake coverage.

### Suggestion 6: GitHub-releases 504 is an outage — `AGENTS-MD-dd3fc45ae9`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-dd3fc45ae9-github-releases-504-is-an-outage.md](./2026-06-08-199/AGENTS-MD-dd3fc45ae9-github-releases-504-is-an-outage.md)

**Proposed agent instruction:**
> **A 504 across multiple unrelated GitHub-releases downloads is an external outage, not a code failure.** "When CI fails on `curl`/`helm` fetches from GitHub releases with 504s across several unrelated downloads (helm charts, binaries), it is a GitHub-releases degradation, not your diff. Re-run the failed jobs once it recovers; do not chase each failure webhook or edit code. Note it in the run summary."
>
> *Grounded in: auto-014, where test_helm_render (two different charts) and the kubeconform install all 504'd within minutes.*

**Justification:** During a stacked-PR run each PR re-runs the full suite, so a transient outage floods identical failure webhooks. Reacting to each — re-running into a degraded dependency, or editing code to "fix" a download that isn't broken — wastes CI and risks a real bug. The tell is the signature: 504 from GitHub releases across DIFFERENT artifacts. Diagnose once, stop chasing, note it, re-kick once after recovery. §6.36 carves out exactly this genuine-external-blip case.

### Suggestion 7: Register a unit test in run.sh (catch-all gates it) — `AGENTS-MD-6a46a8ad7e`
- **Per-rule file**: [./2026-06-08-199/AGENTS-MD-6a46a8ad7e-register-unit-test-in-run-sh.md](./2026-06-08-199/AGENTS-MD-6a46a8ad7e-register-unit-test-in-run-sh.md)

**Proposed agent instruction:**
> **Register a new unit test in tests/unit/run.sh; the catch-all step gates it.** "Adding `run_suite tests/unit/test_X.sh` to tests/unit/run.sh is sufficient to gate a new unit test on push, because unit-tests.yml runs a run.sh catch-all step that is the source of truth for completeness. A per-test workflow step is optional visibility only, and editing .github/workflows/ may be blocked by the push token's missing workflow scope."
>
> *Grounded in: auto-014, where two new unit tests were gated by adding them to tests/unit/run.sh without touching the workflow.*

**Justification:** It is easy to assume a new test must be added to the CI workflow YAML — which both wastes effort and can hit the missing-`workflow`-scope wall on the push token. The workflow is structured so a `run.sh` catch-all runs every wired test and is the documented source of truth; per-test steps are convenience. One line in `run.sh` is necessary and sufficient. The rule saves a dead-end push and the risk of an un-gated test.
