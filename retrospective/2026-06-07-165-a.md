## Part 1 — what happened

The build phase (first retro) closed with five follow-up open-issues, each carrying
candidate mechanisms but no decision. In this tail the user adjudicated them in chat,
and — critically — the AWS account expired mid-conversation, converting the run from
"implement" to "capture durably for a fresh-account session."

Key decisions the user made:
- **Secrets:** ESO (`PushSecret` + `ExternalSecret`, `generatorRef`) is the default
  for secret movement/generation in *every* cluster; `XPlatformSecret` is reserved
  for AWS-resource-grade management (KMS/replica/policy/tags); **do not retrofit
  working XPlatformSecret usages.** The ESO `PushSecret` capability (writes/creates a
  provider entry from a k8s Secret or generator) was the finding that made the
  all-ESO path complete and dissolved the earlier "who writes to Secrets Manager?"
  caveat. Recorded as **ADR 0005**.
- **Config vs. app:** cluster facts (domain/region/cert-ARN/role-ARN) belong in a
  per-cluster ConfigMap owned by the cluster XRD and read by add-ons — not threaded
  through per-app Helm overlays. Workloads stay cloud-agnostic. This also dissolves
  the bootstrap-selfHeal-vs-overlay conflict (no need to pause bootstrap).
- **ESO everywhere:** ESO + an IRSA ClusterSecretStore is a baseline component of
  every cluster, provisioned by the `XPlatformCluster` abstraction.
- **Process:** the user granted standing permission to override the harness
  single-branch directive when stacked PRs are requested (recorded in the skill).

Outputs: ADR 0005 (adopted), the handoff rewritten with an explicit ordered
new-session task list, the open-issues register updated with decisions + a status
index, and the stacked-PR skill amended.

## Part 3 — agents-file suggestions

### Suggestion 1: Keep cluster facts in a per-cluster ConfigMap; workloads cloud-agnostic — `AGENTS-MD-4a863eb684`

- **Per-rule file**: [./2026-06-07-165-a/AGENTS-MD-4a863eb684-cluster-facts-configmap-cloud-agnostic-workloads.md](./2026-06-07-165-a/AGENTS-MD-4a863eb684-cluster-facts-configmap-cloud-agnostic-workloads.md)

**Proposed agent instruction:**

> **Keep cluster facts in a per-cluster ConfigMap and workloads cloud-agnostic.** "Cluster-level facts (domain, region, ACM cert ARN, IRSA role ARNs) belong in a per-cluster ConfigMap provided by the cluster abstraction and read by platform add-ons; do NOT thread them through per-application Helm value overlays, and keep workload apps cloud-agnostic (no ARNs/region/provider knowledge) so they neither know nor care which cloud they run on."
>
> *Grounded in: auto-012 — per-app cert-ARN/domain/role-ARN Helm overlays fought bootstrap selfHeal; the user called this out as a smell.*

**Justification:** auto-012 threaded account-ephemeral AWS facts through per-app Helm `valuesObject` overlays, which (a) bootstrap selfHeal kept reverting and (b) leaked AWS specifics into workloads that have no business knowing them. The user's framing — "an app should not need to know what region it is in, or the ARN of anything" — is the durable principle. A per-cluster ConfigMap consumed by add-ons removes both problems at once and keeps workloads portable. Marginal cost: one ConfigMap per cluster; cost of the smell: a recurring selfHeal fight plus non-portable apps.

### Suggestion 2: Apply new conventions forward-only; do not retrofit working systems — `AGENTS-MD-0f876677e7`

- **Per-rule file**: [./2026-06-07-165-a/AGENTS-MD-0f876677e7-forward-only-no-retrofit.md](./2026-06-07-165-a/AGENTS-MD-0f876677e7-forward-only-no-retrofit.md)

**Proposed agent instruction:**

> **Apply new conventions forward-only; do not retrofit already-working systems.** "When adopting a new convention or preferred mechanism, apply it forward-only; do NOT retrofit already-working implementations to the new pattern unless they are broken or the migration has a concrete payoff, because churning working code for stylistic consistency risks regressions for no behavioural gain."
>
> *Grounded in: auto-012 — the user explicitly said "do not go back and retrofit working XPlatformSecrets" when adopting the ESO-default philosophy.*

**Justification:** When the ESO-default decision landed, the instinct could have been to migrate the existing working `XPlatformSecret` usages to plain ESO for consistency. The user explicitly forbade that: working code should not be churned for a stylistic convention change. This generalizes — new conventions are forward-looking defaults, not retroactive mandates. Cost of the rule: occasional mixed mechanisms; cost of ignoring it: needless regression risk in code that already worked.

### Suggestion 3: Honor an explicit stacked-PR request over the harness single-branch directive — `AGENTS-MD-bb50c47dc4`

- **Per-rule file**: [./2026-06-07-165-a/AGENTS-MD-bb50c47dc4-stacked-pr-overrides-harness-branch-directive.md](./2026-06-07-165-a/AGENTS-MD-bb50c47dc4-stacked-pr-overrides-harness-branch-directive.md)

**Proposed agent instruction:**

> **Honor an explicit stacked-PR request over the harness single-branch directive.** "When the user explicitly asks for stacked PRs, use the stacked-PR workflow even if the harness pinned the session to one branch; the owner has given standing permission (recorded in the stacked-pr-on-feature-branch skill) to override the branch-shape directive for that request, while still never committing to main and keeping all other PR/test discipline."
>
> *Grounded in: auto-012 — the user noted agents keep refusing stacked PRs because the harness says one-branch, and granted a standing override.*

**Justification:** The user observed that "most sessions, even when instructed to use stacked PRs, don't want to because the agent harness instructs them to just use one branch" — and this very session honored the single-branch directive over the skill default. The owner's standing permission resolves the conflict: an explicit stacked-PR request wins. Scope is narrow (branch shape only); no other discipline is waived. Cost of the rule: none; cost of ignoring it: the user's explicit workflow preference is silently overridden every session.
