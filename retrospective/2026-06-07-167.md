## Part 1 — what happened

### Phase 1 — secret-handling decisions (ADR 0005)
Adjudicated the five auto-012 follow-ups in chat. The owner chose ESO
(`PushSecret`+`ExternalSecret`, `generatorRef`) as the default for secret movement in
every cluster, reserving `XPlatformSecret` for AWS-resource-grade management, and
forbade retrofitting working secrets. The ESO `PushSecret` capability (write/create a
provider entry from a k8s Secret) was the finding that dissolved the "who writes to
Secrets Manager?" caveat. Captured as `docs/decisions/0005-*` (adopted).

### Phase 2 — the testing-philosophy correction arc (the spine of the session)
A sequence of owner corrections, each sharpening the same point, each exposing a wrong
default I had reached for:
- Static `yq`/`grep` "unit tests" are **lints, not tests** — they never catch "we told
  the platform to create X but X never got created" (OI-2026-06-07-6).
- "Run real verification **nightly**" is wrong — verification is **coupled to the
  change**, run every time, against what you built.
- **CI ≠ the build**: GitHub Actions runs at PR time, decoupled from the real build;
  cluster-requiring tests (even kind) must be `workflow_dispatch`-only, not push/PR.
- **"Disable" is a profile**, not a switch: `full` (dev) / `verify-only` (mature, fast)
  / `off`.
Each correction was recorded durably (open-issues + handoff + constraint-correction
notes) before moving on.

### Phase 3 — a multi-round adversarial planning process
At the owner's direction, produced the test-overhaul plan via: **3 independent plans**
(1 lead-authored, 2 persona subagents) → **9 round-1 adversarial reviews** (3 personas
× 3 plans) → **synthesis** → **5 round-2 reviews** (3 personas + the 2 plan-authors as
adversaries) → **2 owner corrections mid-flight** → **5 round-3 reviews** → finalization
+ revision passes → `FINAL-PLAN.md`. ~26 subagents across the run, all writing full
artifacts to files and returning ≤150-word summaries to keep the lead context intact.
The reviews repeatedly caught (a) factual errors only tree-grounding surfaces
(`source: IRSA` not `InjectedIdentity`; v1-vs-v2 claim-verify; Pipeline-mode parsing;
spoke endpoint is public), and (b) a **false constraint I had propagated** ("can't edit
workflows") plus an **invented distinction with no referent** ("build ≠ CI" — the build
*is* a `workflow_dispatch` job).

## Part 3 — agents-file suggestions

### Suggestion 1: Verify a constraint against the repo/owner before encoding it into subagent briefs — `AGENTS-MD-a632612c7e`
- **Per-rule file**: [./2026-06-07-167/AGENTS-MD-a632612c7e-verify-premise-before-fanout.md](./2026-06-07-167/AGENTS-MD-a632612c7e-verify-premise-before-fanout.md)

**Proposed agent instruction:**
> **Verify a constraint against the repo or owner before encoding it into subagent briefs.** "Before baking a constraint or premise into briefs that fan out to many subagents or many review rounds, verify it against the repo and (if it is owner-policy) the owner; a false premise propagates across every downstream agent and round and is expensive to unwind."
>
> *Grounded in: 2026-06-07 — the false "can't edit workflows" premise (and the CI-as-trigger framing) seeded 3 source plans, 14 reviews, and the synthesis before two owner corrections unwound it.*

**Justification:** I encoded "this environment can't edit `.github/workflows/*`" into the synthesized plan and the round-2/round-3 briefs. It was false (jentic Contents-PUT edits workflows — established earlier in this very session), and the owner had to correct it; a second false framing ("the build isn't CI") followed. By then it had propagated through three source plans, fourteen reviews, and a synthesis, forcing two correction notes and two revision passes. The marginal cost of one verification (a grep, or one question to the owner) is tiny; the cost of a false premise in a fan-out is multiplied by every agent and round downstream.

### Suggestion 2: Ground architectural framings in real repo artifacts — `AGENTS-MD-b157e3e0e1`
- **Per-rule file**: [./2026-06-07-167/AGENTS-MD-b157e3e0e1-ground-framings-in-artifacts.md](./2026-06-07-167/AGENTS-MD-b157e3e0e1-ground-framings-in-artifacts.md)

**Proposed agent instruction:**
> **Ground architectural framings in real repo artifacts, not invented distinctions.** "Do not introduce an architectural distinction or named mechanism that has no referent in the actual repo; verify the artifact exists (the workflow, the script, the field) before building a plan on it, because a phantom distinction survives until an adversary greps for it."
>
> *Grounded in: 2026-06-07 — the plan's "build ≠ CI" split had no referent (there is no bring-up script; `apply-and-verify` IS a workflow_dispatch job); three round-3 reviewers independently grepped and collapsed it.*

**Justification:** The synthesized plan leaned on a "build (not CI)" execution context as if a separate build executor existed. It didn't — `grep` finds no `apply-and-verify.sh`/`bring-up.sh`; the bring-up *is* a `workflow_dispatch` action in `terraform-test.yml`. The distinction was a comfortable abstraction with no ground truth, and it warped the on-by-default story until round-3 reviewers caught it. One `ls scripts/` at framing time would have prevented a whole revision pass.

### Suggestion 3: Adversarial/synthesis subagents must verify load-bearing claims against the tree — `AGENTS-MD-741e8d0d66`
- **Per-rule file**: [./2026-06-07-167/AGENTS-MD-741e8d0d66-reviewers-verify-against-tree.md](./2026-06-07-167/AGENTS-MD-741e8d0d66-reviewers-verify-against-tree.md)

**Proposed agent instruction:**
> **Adversarial and synthesis subagents must verify load-bearing claims against the tree.** "Brief adversarial and synthesis subagents to verify every load-bearing factual claim against the actual repo files, not just reason about the document; plan-level facts (a ProviderConfig source, a CRD api version, an endpoint flag) are routinely wrong and only tree-grounding catches them."
>
> *Grounded in: 2026-06-07 — tree-grounded reviewers caught `source: IRSA` (not `InjectedIdentity`), v1-vs-v2 claim-verify, Pipeline-mode MR-kind paths, and the spoke being public; document-only reasoning would have shipped all four wrong.*

**Justification:** The highest-value findings across all three review rounds were not opinions — they were *facts checked against the repo*: the AWS ProviderConfig is `source: IRSA` not `InjectedIdentity`; `crossplane-claim-verify` is v1-claim-shaped on a v2 repo; composition MR kinds live under `spec.pipeline[].input.resources[].base`; the spoke EKS endpoint is public. Each would have shipped as a plan error. Reviewers who only reasoned about the prose missed them; reviewers explicitly told to grep the tree caught them. Make tree-verification a required part of every review/synthesis brief.

### Suggestion 4: Finalize commits before dispatching a SHA-gated heavy CI run — `AGENTS-MD-8966d2dd66`
- **Per-rule file**: [./2026-06-07-167/AGENTS-MD-8966d2dd66-finalize-before-sha-gated-dispatch.md](./2026-06-07-167/AGENTS-MD-8966d2dd66-finalize-before-sha-gated-dispatch.md)

**Proposed agent instruction:**
> **Finalize commits before dispatching a SHA-gated heavy CI run.** "Do not push further commits after dispatching a heavy CI run that a verifier gates by exact HEAD SHA; finalize all commits first, then dispatch, or the cached green run never matches HEAD and the gate stays red on work the run already validated."
>
> *Grounded in: 2026-06-07 — repeatedly dispatched chainsaw then pushed docs commits, so chainsaw-verify never matched HEAD; the merge ultimately relied on `mergeable_state: unstable` (non-blocking), not a green gate.*

**Justification:** During the PR-#165 finalization I dispatched chainsaw for a SHA, then pushed docs-only commits, moving HEAD and orphaning the cached green run — three times. chainsaw-verify (an exact-HEAD-SHA gate, §6.7) stayed red on work the run had actually validated. The fix is trivial sequencing: make the last commit, *then* dispatch. (Corollary that unblocked the merge: `mergeable_state: unstable` means mergeable-with-non-blocking-checks, not blocked — don't defer a merge on an assumed-blocked gate.)
