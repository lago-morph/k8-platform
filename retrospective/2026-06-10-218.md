## Part 1 — what happened

### Phase 1 — premise verification before design

Goal: implement the SUBSTRATE-READINESS row-4 keystone (OI-2026-06-07-2), which the
record said was "decided (ADR-0005 cluster-facts ConfigMap), not implemented."
The first load-bearing discovery was that the recorded decision was **not
implementable as written**: tree-grounding showed two of the four facts land in
chart-rendered annotations (the NLB cert ARN on the ingress Service, the IRSA
role ARN on the external-dns ServiceAccount) which cannot read ConfigMaps at
runtime; serving them from a ConfigMap would have required a mutating webhook in
a deliberately audit-only Kyverno posture. The second discovery cut the other
way: the producer chain was further along than the handoff implied —
`crossplane-phase3.tf` already materializes a `cluster-network` EnvironmentConfig
from terraform discovery, `platform-cluster.yaml` already surfaces
`status.certificateArn`, `xspokeaccess.yaml` already surfaces
`status.externalDnsRoleArn`, and the auto-008 design had already put a
`certificate-arn` annotation on the spoke's ArgoCD cluster Secret. The design
practically assembled itself from parts the repo already had: facts ride the
cluster Secret's annotations; per-add-on ApplicationSets template them into helm
values.

### Phase 2 — ADR draft, adversarial review, ratification

The mechanism brief was authored as ADR-0010 and attacked by two tree-grounded
opus reviewers in parallel (one on ArgoCD/ApplicationSet mechanics and
transition semantics, one on contract completeness and producer feasibility).
They returned 5 BLOCKERs and 7 MAJORs, and the BLOCKERs were real: the draft's
kubeconform verification promise was hollow (no ApplicationSet schema was ever
fetched; `--ignore-missing-schemas` would have silently skipped the new kind),
the cutover was claimed seamless when it is a genuine delete-then-recreate
window, the hub-side alloy app structurally cannot share an ApplicationSet with
the spoke apps (and auto-008 had explicitly *rejected* the cluster generator
over the exact hub-destination hazard the draft re-introduced), keycloak's DB
host/port don't reduce to cluster facts at all (third XR), and `region` had no
surfaced producer source (the draft's "EnvironmentConfig" claim was false —
verified absent). The revised ADR grew the contract to five per-Secret-complete
facts, scoped keycloak DB out with a named PR-2 path, restructured to per-add-on
sets with selector scoping, recorded the auto-008 F1 reversal with new
rationale, and added an honest cutover section. The owner ratified via a single
question (recommended option taken) and implementation proceeded.

### Phase 3 — implementation

Ten Application files became seven ApplicationSets (`missingkey=error`,
`preserveResourcesOnDeletion`, waves on template metadata, destination
`{{.name}}`, names prefixed by the `short-name` label so PR #210's `spoke-hello`
live check stays valid). The workload1-* mirror files collapsed into the shared
sets — the "phase-6 ApplicationSet refactor" the repo had been deferring arrived
as a by-product. Alloy got its own deliberately hub-pinned set; its River-config
placeholders became `sys.env()` lookups fed by template-injected `alloy.extraEnv`
(helm values cannot patch inside a config string — verified `sys.env` and
`extraEnv` against live Grafana docs after the context7 MCP quota was exhausted).
Bycatch fixed along the way: workload1's external-dns values were missing the
auto-012 IRSA pins (`serviceAccount.name`, `--aws-zone-match-parent`) — a latent
drift bug that would have silently broken workload1 DNS on its first live
bring-up; `bootstrap.yaml` carried a fictional `SyncWaves=true` syncOption; the
kubeconform argo CRD store was pinned to v2.13.1 while the deployed chart (6.7.3)
is ArgoCD v2.10.4 — pin aligned and the ApplicationSet schema added so the new
kind is actually validated.

### Phase 4 — tests, docs, merge

Four app-contract suites were rewritten onto `.spec.template.*` paths; a new
bidirectional contract lint (`test_cluster_facts_contract.sh`) gates template
fact references ⊆ the ADR's contract keys, the retirement of all
OVERLAID-AT-REGISTRATION markers, and hello's cloud-agnosticism. Two near-misses
surfaced here (see §3.4): the new test was silently NOT enumerated (run.sh is an
explicit list, not a glob), and three composition-render failures turned out to
be environmental (dockerd not started) rather than regressions. Docs closed the
loop: ADR-0005's corollary marked amended, SUBSTRATE row 4 → "consumer half
committed, pending clean-build verification, blocked on row 5", open-issues
entry/index updated, handoff quickstart rewritten. Full unit suite green locally
and in CI; PR #218 opened with an honest done-contract section and merged by the
owner.

## Part 3 — remedy proposals (classified per `ai/LESSONS.md` §3)

### Proposal 1 — run.sh enumeration drift lint (classification: **(a) mechanical check**)

**Event:** `test_cluster_facts_contract.sh` was written, passing, executable —
and ran **zero times** in the full suite, because `tests/unit/run.sh` is an
explicit `run_suite` list, not a glob. Caught only by an ad-hoc
`grep -c` of the suite output before the final commit. A non-running test that
exists is worse than no test: it reads as coverage. This is the exact failure
class OI-2026-06-07-6 ("static assertions masquerade as tests") names, one
level up.

**Check design:** a self-test at the top of `run.sh` (or a tiny
`test_run_sh_enumerates_all.sh`, itself enumerated first):
`for f in tests/unit/test_*.sh; do grep -q "run_suite tests/unit/$(basename "$f")" tests/unit/run.sh || fail; done`
— fail-closed, zero false positives (deliberate exclusions get an explicit
`# run_suite-exempt: <reason>` marker the loop honors). Cost: ~6 lines, runs in
milliseconds.

**ADOPTED** (this PR, L30): completeness guard inside `tests/unit/run.sh`
itself — no new file. It proved itself red-first by catching Proposal 2's new
lint before that lint was enumerated.

### Proposal 2 — pin-skew lint between the kubeconform CRD store and deployed chart versions (classification: **(a) mechanical check**)

**Event:** the argo CRD schemas were pinned to v2.13.1 while the deployed chart
6.7.3 ships ArgoCD v2.10.4 — a silent skew that meant kubeconform was validating
manifests against a controller three minors ahead of the one that admits them.
It sat undetected since the store was created; a reviewer found it only because
the ADR forced the question.

**Check design:** record `ARGOCD_APP_VERSION="v2.10.4"` in `versions.env` next to
`argocd_version` (chart), and lint that (1) every argo URL in
`scripts/fetch-crds-for-kubeconform.sh` contains `$ARGOCD_APP_VERSION`, and
(2) a comment in `variables.tf` ties chart→app version so a chart bump forces
the pair. Generalizes to the ESO/Kyverno/provider pins the fetch script already
hardcodes. Cost: one env var + a ~10-line grep lint.

**ADOPTED** (this PR, L31) with a stronger shape than proposed: instead of
linting two hardcoded copies, the duplication was removed — the fetch script now
*sources* `versions.env` and interpolates `ARGOCD_APP_VERSION`; the lint
(`test_version_pin_consistency.sh`, written to absorb future pin pairs rather
than spawn siblings) holds only the one unavoidable duplicate (the terraform
variable default) equal and forbids hardcoded argo versions from reappearing in
the fetch script.

### Proposal 3 — `argocd/**` is not on the live-evidence gate's trigger paths (classification: **(c) structural proposal for the owner**)

**Event:** this PR rewired what every spoke cluster runs, entirely within
`argocd/**` — and the live-evidence gate did not arm, because its trigger paths
cover `crossplane/**`/`policies/**`/`terraform/**` only. That was convenient
here (the change is genuinely static-verifiable and inert without a labeled
Secret) but the asymmetry is real: GitOps-synced manifests are *more* live-coupled
than Compositions (ArgoCD applies them on merge with no dispatch), yet they
carry no live-evidence obligation. Owner decision needed on whether `argocd/**`
(and `platform-services/**`) should arm the gate, possibly with an
inertness carve-out — this is gate design, not something an agent should widen
or narrow unilaterally.

### Proposal 4 — adversarial review of recorded-but-unbuilt decisions before implementing them (classification: **(d) observation; existing enforcement sufficient**)

**Event:** the recorded resolution ("cluster-facts ConfigMap", named in three
documents and a readiness row) was infeasible for two of its four facts. Had
implementation started from the record without tree-grounding, the session would
have built a mutating-webhook detour or stalled. The existing AGENTS.md rules
("verify every premise against the repo before fanning out"; "high-stakes plans
get adversarial review") fully covered this — the review caught 3 BLOCKER-grade
false claims in my own draft (hollow verification, impossible alloy fold,
seamless-cutover fiction) plus 2 in the record (`region` source, keycloak DB
scope). No new rule needed; recorded here as evidence the mechanism earns its
cost: 2 subagents ≈ 10 minutes wall-clock bought 12 design corrections before a
line of implementation.

### Proposal 5 — environmental-failure check before re-diagnosing "broken" tests (classification: **(d) observation**)

**Event:** three composition-render tests failed mid-session with golden
mismatches *and* docker-daemon errors; the cause was dockerd not yet started in
the sandbox, not the changes (which never touched `crossplane/`). The failure
log was read first (per AGENTS), the daemon started, all green. Counter-example
worth recording because the same signal ("render tests red after my PR") has
historically triggered code archaeology. No rule change — the existing
"read the failure log before theorizing" line was sufficient and worked.
