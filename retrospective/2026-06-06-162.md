## Part 3 — agents-file suggestions

### Suggestion 1: GitOps-deliver Crossplane provider credentials — `AGENTS-MD-e4dc06137e`
- **Per-rule file**: [./2026-06-06-162/AGENTS-MD-e4dc06137e-gitops-deliver-provider-credentials.md](./2026-06-06-162/AGENTS-MD-e4dc06137e-gitops-deliver-provider-credentials.md)

**Proposed agent instruction:**
> **GitOps-deliver Crossplane provider credentials, never leave them as manual bootstrap steps.** "Any resource every composition depends on — the shared `ClusterProviderConfig`/`ProviderConfig`, provider runtime configs — must be delivered by terraform or a GitOps app, never a one-off `kubectl apply` documented in a plan. A manual step is absent on every rebuilt cluster and silently stalls all managed resources."
>
> *Grounded in: auto-011 blocker #2 — the missing ClusterProviderConfig/default (SEG-1 §0c manual step) stalled all 11 platform-cluster MRs.*

**Justification:** The ClusterProviderConfig was documented as a manual `kubectl get || kubectl apply` in a plan doc and never automated. On the rebuilt cluster it was simply gone, and every AWS MR sat `CannotConnectToProvider` with zero AWS API calls — invisible until a CI kube-diagnose dumped the MR conditions (~30 min of diagnosis). The marginal cost of the rule is one manifest in the GitOps tree; the cost of skipping it is a fully-stalled control plane on every fresh account.

### Suggestion 2: Explicit IRSA runtimeConfigRef on child providers — `AGENTS-MD-131bccdc47`
- **Per-rule file**: [./2026-06-06-162/AGENTS-MD-131bccdc47-child-provider-irsa-runtimeconfigref.md](./2026-06-06-162/AGENTS-MD-131bccdc47-child-provider-irsa-runtimeconfigref.md)

**Proposed agent instruction:**
> **Give every child AWS provider an explicit IRSA `runtimeConfigRef`.** "In the Upbound family model each child provider (eks/iam/acm/route53/secretsmanager/rds) runs its own pod under its own ServiceAccount. Set `spec.runtimeConfigRef` on every child Provider to the IRSA-annotated DeploymentRuntimeConfig (or ensure its SA is annotated and the role trust admits it); otherwise the pod has no web-identity token and every MR fails `token file name cannot be empty`."
>
> *Grounded in: auto-011 blocker #3 — only the family SA had the role-arn annotation; all child pods lacked IRSA.*

**Justification:** The family Provider referenced the IRSA DeploymentRuntimeConfig; the six child providers did not, so their pods got default un-annotated SAs. With the role trust pinned by `StringEquals` to the single family subject, no child could assume the role — every cluster MR stalled. Diagnosing it took a provider-pod/SA dump via CI. One `runtimeConfigRef` block per child provider prevents a whole class of "MR never reconciles, no AWS error" stalls.

### Suggestion 3: Live-read via ArgoCD API / kube-diagnose when kube-API is blocked — `AGENTS-MD-23d3a37959`
- **Per-rule file**: [./2026-06-06-162/AGENTS-MD-23d3a37959-live-read-without-kube-api.md](./2026-06-06-162/AGENTS-MD-23d3a37959-live-read-without-kube-api.md)

**Proposed agent instruction:**
> **Read live kube state via the ArgoCD REST API or a kube-diagnose workflow when the kube-API is unreachable.** "The sandbox cannot reach the private-CA EKS kube-API (client cert fails; `--insecure` makes the egress gateway 503). Do not burn time on kubectl. Use the ArgoCD `applications/{app}/resource` REST endpoint for managed resources, and the `kube-diagnose` `workflow_dispatch` job (read-only script input) for arbitrary cluster reads."
>
> *Grounded in: auto-011 — kubectl confirmed structurally blocked; the ArgoCD API + kube-diagnose workflow carried all live diagnosis.*

**Justification:** Two independent kubectl attempts failed exactly as the prior handoff predicted (~3 wasted min). The ArgoCD REST API returned the XR's full status/conditions instantly, and a small `workflow_dispatch` diagnostic gave arbitrary `kubectl` output from CI. Naming these as the default live-read tools saves every future session the kubectl dead-end.

### Suggestion 4: Verify provider CRD field names before merging composition code — `AGENTS-MD-5b8f287c0a`
- **Per-rule file**: [./2026-06-06-162/AGENTS-MD-5b8f287c0a-verify-crd-fields-before-merge.md](./2026-06-06-162/AGENTS-MD-5b8f287c0a-verify-crd-fields-before-merge.md)

**Proposed agent instruction:**
> **Verify provider CRD field names against the live cluster before merging composition code.** "`crossplane render` and kubeconform validate against locally-authored schemas, not the live provider CRDs, so a wrong `forProvider`/`status` field name passes locally and fails only at apply. Dump the real CRD schema (e.g. via kube-diagnose) and confirm the field names/enums before merging a new Composition."
>
> *Grounded in: auto-011 — XSpokeAccess subagent flagged 3 uncertain fields; a live CRD dump confirmed all 3 before merge.*

**Justification:** The subagent's render+kubeconform passed but it explicitly couldn't know whether `AccessEntry.status.atProvider.accessEntryArn`, `OpenIDConnectProvider.status.atProvider.arn`, or `AccessEntry type: STANDARD` matched the live provider. One CRD-schema dump confirmed all three, turning "merge and hope" into "merge with evidence." The check is one kube-diagnose run; the alternative is a failed apply discovered 20 minutes into a management cycle.
