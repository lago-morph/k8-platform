## Part 1 — what happened

After committing the main retro, I dispatched the full chainsaw set against
`6e03d8b` to validate phase 2 and turn `chainsaw-verify` green (§6.7). It failed
(run 27072199866). Reading the log first (§6.9): the phase-2 scenarios
(`composition-drift`, `claim-rotation`, `xrd-establishes`, `claim-deletion-cleanup`,
`smoke`, `xdatabase-xrd-establishes`) all **passed**; three failed —
`claim-creates-secret` (the known OI-2026-05-28-1 ASM flake, 246s timeout) and the
two **real-AWS** xdatabase scenarios (`01-claim-creates-rds`, `02-deletion-cleanup`),
which failed in ~35s because the kind-only harness has no provider-aws-rds and
cannot provision RDS.

The xdatabase scenarios already carried a `REAL-AWS / NIGHTLY — DO NOT run in the
per-PR kind-only matrix` header — but `tests/chainsaw/run.sh` only ever partitioned
out `meta-` dirs and never read that header, so the gate was inert. Fix (`fab6026`):
run.sh now excludes any scenario carrying the marker unless
`CHAINSAW_INCLUDE_REALAWS=1`, with a regression guard
(`test_chainsaw_realaws_gated.sh`) and an open-issue note (OI-2026-06-06-4). The
re-dispatched chainsaw on `fab6026` went **green**.

A small process miss surfaced at merge time: I pushed the handoff docs commit
(`e41c5ad`) on top of the green `fab6026`, so the SHA-matched `chainsaw-verify`
check reded (it gates on a green chainsaw run whose head_sha equals HEAD). The
merge still went through, but the red check was avoidable.

The user then said "Merge everything"; I confirmed the chainsaw was green on
`fab6026` (identical code to HEAD bar the handoff doc) and merged PR #159 into
`main` (`c8128cb`).

## Part 3 — agents-file suggestions

### Suggestion 1: Gate expensive real-cloud chainsaw scenarios out of the per-PR kind matrix — `AGENTS-MD-d511ae497d`

- **Per-rule file**: [./2026-06-06-159-a/AGENTS-MD-d511ae497d-gate-realaws-chainsaw-out-of-per-pr-matrix.md](./2026-06-06-159-a/AGENTS-MD-d511ae497d-gate-realaws-chainsaw-out-of-per-pr-matrix.md)

**Proposed agent instruction:**

> **Gate expensive/real-cloud chainsaw scenarios out of the per-PR kind matrix.**
> "A chainsaw scenario that provisions live cloud resources (an RDS instance, a
> real EKS cluster, anything taking minutes or needing a provider the kind harness
> does not install) MUST mark itself with a `REAL-AWS / NIGHTLY` header AND be
> excluded from the default per-PR run by `tests/chainsaw/run.sh` unless
> `CHAINSAW_INCLUDE_REALAWS=1`. A documentation-only do-not-run-me-here header is
> not enough — run.sh must actually skip it, or it reds every push in ~35s when the
> resource cannot be created. Author-time coverage stays via render-fixtures + unit
> tests; the live flow runs in the dedicated live step or a nightly real-AWS
> workflow."
>
> *Grounded in: auto-010 chainsaw run 27072199866.*

**Justification:** Two xdatabase scenarios that provision a live RDS instance ran
in the kind-only matrix (no provider-aws-rds) and failed in ~35s, reding the whole
chainsaw run even though every phase-2 scenario passed. They already documented
"DO NOT run in the per-PR matrix" in a header that run.sh never read. The marginal
cost of real gating is one grep + one env var; the cost of not having it is a red
heavy-CI check on every push, a blocked merge, and the risk of unmonitored
real-cloud provisioning (and orphans).

### Suggestion 2: Re-run the SHA-matched heavy-CI verifier after any post-green push — `AGENTS-MD-a030761ad1`

- **Per-rule file**: [./2026-06-06-159-a/AGENTS-MD-a030761ad1-rerun-sha-matched-verifier-after-post-green-push.md](./2026-06-06-159-a/AGENTS-MD-a030761ad1-rerun-sha-matched-verifier-after-post-green-push.md)

**Proposed agent instruction:**

> **Re-run the SHA-matched heavy-CI verifier after any push that lands on top of a
> green heavy run.** "When a heavy workflow (chainsaw, terraform-test) is
> dispatch-verified by a push-triggered checker that matches the run head_sha
> (AGENTS 6.7), do not push further commits — even docs-only — after the green
> heavy run without either re-dispatching the heavy run on the new HEAD or
> re-running the verifier. The verifier gates on a green run whose head_sha equals
> the PR HEAD; a commit on top moves HEAD past the cached green SHA and the
> verifier reds even though the code is unchanged."
>
> *Grounded in: auto-010 chainsaw-verify red on docs commit e41c5ad after chainsaw passed on fab6026.*

**Justification:** After chainsaw went green on `fab6026`, a docs-only handoff
commit pushed on top moved the PR HEAD to `e41c5ad`; chainsaw-verify gates on a
green run whose head_sha equals HEAD, so it reded despite byte-identical code. A
single misordered docs push produced a red required check at merge time; the
remedy is a single re-run or re-dispatch — order the docs commit before the heavy
dispatch, or re-run the verifier after.
