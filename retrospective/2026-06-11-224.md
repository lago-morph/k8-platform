## Part 1 — what happened

### Phase 1 — brief, adversarial review, reconciliation (PR #220 design)
The ADR-0010 PR-2 producer required resolving four explicitly-deferred
decisions. A design brief was written first
(`planning/adr-0010-cluster-facts/adr0010-pr2-producer-brief.md`), then two
adversarial reviewer subagents ran in the background (one P&T-mechanics, one
architecture/contract) while uncontested work proceeded. The reviews changed
the shipped design materially: (1) ADR-0005's Alternatives section had
*explicitly rejected* provider-kubernetes for this Secret — the reversal
needed an in-place amendment, not a footnote; (2) my `platform-<shortName>`
Secret naming would have broken every workload spoke against the
`platform-spoke` AppProject destination allowlist (`platform-workload1`
matches neither `platform-spoke` nor `*-spoke`) — switched to
`<subdomain>-spoke`; (3) my claim that a Required-policy patch fails the
whole function pipeline was **refuted from upstream source** (v0.10.6 skips
only that one composed resource) — which turned a planned `%.0s` fmt-trick
canary label into the much cleaner Required-gated complete-or-absent design;
(4) a free-text `clusterXRName` observe target was replaced by the
own-name/namespace pairing convention so a typo is observe-not-found (loud),
never a wrong-cluster read. Live-docs verification (raw CRD YAMLs after
Context7 quota ran out) confirmed the namespaced Object/ClusterProviderConfig
schemas and that ESO v0.9.13 *can* template annotations from remote data —
the fork was decided on data flow, not capability.

### Phase 4 — the mid-build defect (PR #223, OI-2026-06-10-1)
The XR sat `Ready=False` on `cluster-cert-validation` for 50+ minutes while
AWS showed the cert ISSUED. Diagnosis chain: MR events showed active retries
("referenced field was empty") → the Certificate MR was Ready with
`status.atProvider.arn` populated → but its `crossplane.io/external-name`
annotation was **empty** — the field the selector's reference extractor
reads. Same v2.5.0 identity bug class as tf-aws#45303. Fix: route the ARN
through the composite (Required patches), merged as #223; the live MR
unstuck via GitOps propagation alone. Every static layer had been green —
only the build-coupled behavioral loop could catch this, which is the
ADR-0006 thesis demonstrated end-to-end.

## Part 3 — remedy proposals (LESSONS §3 classification)

Per the 2026-06-10 amendment, no `AGENTS-MD-*` files; each remedy is
classified per `ai/LESSONS.md` §3.

### R1 — Lint: no provider reference-selectors on provider-written identity (class a: mechanical check)
A unit lint that flags any `*Selector:`/`*Ref:` in
`crossplane/compositions/**` whose referenced composed resource does NOT get
an explicit `crossplane.io/external-name` patch in the same Composition.
The `certificateArnSelector` failure (OI-2026-06-10-1) was exactly this
shape: selectors resolve via the referenced MR's external-name, and
identity-from-provider resources (ACM Certificate) never get one written
back under v2.5.0. The IAM/EKS selectors in the same file are safe *only*
because those MRs carry explicit external-name patches — the lint encodes
that distinction. Cost: one grep-class test; catches the whole class at PR
time instead of 50 live minutes. Companion ADR draft: ADR-0e5ccd45c3.

### R2 — chainsaw-verify waits for an in-flight chainsaw run (class a: mechanical check)
The verifier ran at PR-open, 4 minutes before the already-dispatched
chainsaw run for the same SHA finished, and reported red; the remedy was a
manual lookup re-run. Change `.github/workflows/chainsaw-verify.yml` to
poll for up to ~10 min when a chainsaw run for the HEAD SHA exists
`in_progress` before concluding absent. Removes a whole category of
"re-run the verifier" toil. (Workflow edits route through the jentic
bridge — push token lacks `workflow` scope.)

### R3 — pin the kind binary to its GitHub-releases URL (class a: mechanical check)
`chainsaw.yml` downloads kind from `kind.sigs.k8s.io/dl/...`, which timed
out for 268s and killed a run before any scenario executed.
`github.com/kubernetes-sigs/kind/releases/download/...` serves the same
artifact from infrastructure the runner already reaches. One-line workflow
change (jentic bridge), eliminates an observed flake source.

### R4 — verifier workflows do not fire on a new branch's first push (class d: observation, needs one diagnosis pass)
`chainsaw-verify`/`live-evidence-verify` (push-triggered, path-filtered)
produced **zero** runs for the three stack branches' initial pushes despite
matching paths, but DID fire on #223's branch first push. Inconsistent;
undiagnosed. If confirmed, the fix is adding `pull_request` triggers — but
diagnose before changing (AGENTS: a signal that pattern-matches a known
failure may have a different cause).

### R5 — `ai/environment.md` additions (class: environment-fact routing per LESSONS §3.1)
Two verified sandbox facts: (1) unauthenticated `api.github.com` calls from
the sandbox rate-limit quickly — poll via the authenticated GitHub MCP tools
or timed background wake-ups, never raw curl loops; (2) `actions_list`/
`get_workflow_run` MCP results can exceed the context cap — they auto-save
to a file; parse with `python3 json` against the saved path instead of
re-calling.

### R6 — when a generated artifact depends on a just-edited source, verify the change is *in* the generated output (class d: observation)
My platform-cluster XRD edit failed (read-before-edit guard), I proceeded,
and the regenerated kubeconform schema silently matched the OLD content. The
only reason it was caught in-session was a `grep -c clusterCaData` on the
generated file returning 0. The session already practiced the remedy;
recording the observation rather than proposing a rule (the harness error
WAS loud — the failure was mine to not re-issue the edit).
