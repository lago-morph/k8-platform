## Part 1 — what happened

### Phase 1 — Pick up an in-flight, paused PR2

Session opened mid-procedure. A prior session had reached Step 5 of the `external-api-bridge` meta-skill (live-fire execution) and stopped because the initial `workflow_dispatch` call returned 401 — the jentic credential for `api.github.com` was a personal-scope PAT that couldn't see `lago-morph/k8-platform`. PR1 was already merged; PR2 was waiting on the token problem.

The user opened with a single word ("stop") which I'd already received before the session started — i.e., the prior context had paused. I confirmed clean state and waited.

### Phase 2 — Diagnose the PAT scope problem

User asked: *"Can I generate one [a PAT] there [in the lago-morph org]?"* I walked through fine-grained PAT generation against an org resource owner, including the org-level "Allow access via fine-grained PATs" setting and the four minimum repository permissions (`Actions: read+write`, `Contents: read`, `Metadata: read`). The previous token had been generated against the personal account, so it had no path to org-owned repos regardless of how its repo-scope was set. This is a class of mistake that's easy to repeat — and worth an agents-file rule (see Suggestion 1).

### Phase 3 — Live-fire the four PR2 endpoints

User regenerated the PAT, replaced the jentic credential, said "ok, try now". I re-fired the dispatch. The original 401 was gone — replaced by a 400 from GitHub: *"Provided value '0' for input 'phase' not in the list of allowed values."* I'd guessed at the workflow's input enum. One quick grep of `.github/workflows/terraform-test.yml` and the right value (`phase=test, action=test-unit`) succeeded with a 204.

`phase=test action=test-unit` turned out to be the perfect live-fire vehicle: it completes in under 30 seconds, mutates nothing in AWS, and exercises a full dispatch → list-runs → list-jobs → download-logs chain. The run completed before I'd finished the next probe.

### Phase 4 — Discover two catalog/bridge gaps

Walking the remaining endpoints in order surfaced two real problems:

1. **`actions/get-workflow-run` is missing from jentic's catalog.** Multiple searches confirmed it: the catalog returns list-runs, list-jobs, get-usage, rerun, but not the single-run GET. Workaround: filter `list-workflow-runs` by `id` — the same fields (`status`, `conclusion`, `created_at`, `html_url`, `run_number`) appear on each list entry. Bandwidth cost is trivial for this project's volume.
2. **`actions/download-workflow-run-logs` returns 500 through jentic.** GitHub's contract is a 302 redirect to a short-lived signed URL pointing at a zip archive of all per-job logs concatenated. jentic doesn't follow the 302, so the call dies inside the bridge. Workaround: enumerate jobs via `list-jobs-for-workflow-run`, then call `download-job-logs-for-workflow-run` per job. For `terraform-test.yml`'s current shape (one job per run) this is a one-extra-call substitute.

Both workarounds were verified by running them — not just designed on paper.

### Phase 5 — Author the skill

User told me directly: *"make sure that these workarounds make their way into the new skill. You should also put dates next to when you last verified the workflow."* This was the key instruction of the session. It would have been easy to author a clean SKILL.md that listed the four working endpoints and silently omitted the two broken ones — and a future agent would then trip over the same gaps next month.

I authored:
- Four `resources/*.json` files, each with `endpoint_ref` (the `op_*` UUID), `recorded_at` (ISO timestamp), `last_verified` (date), `verified: true`.
- One `SKILL.md` with a dedicated **§3 Catalog gaps & workarounds** section that names both broken endpoints, points at the substitute, and gives a re-check trigger condition. The endpoints table surfaces `Last verified` per row.
- One paragraph added to `ai/testing-guidelines.md` §9 covering the jentic outage / handoff fallback (PR2-scope deliverable from the spec).

PR #30 opened as draft, no CI gates (skills-only change), merged within minutes.

### Phase 6 — User asked about tests

The session's final substantive question: *"Do you have any unit or integration tests for either of these skills?"* I answered honestly: no — verification is procedural (live-fire + pre-commit checklist), `tests/` is entirely for the Terraform harness. The spec explicitly judged automated lint out of scope (§7) because total project volume is 10–20 dispatches ever. I offered three optional additions ranked by ROI; user did not ask for any of them. Recorded as a future possibility.

## Part 4 — proposed ADRs

Architectural decisions made in this session that the user *might* want to record formally. Titles only — author via the `adr` skill if you decide they're worth it.

- **Substitute conventions for absent or broken jentic-bridged endpoints** — Records the two patterns established this session (filter-by-id for missing single-resource GETs; split-call enumerate-then-fetch for endpoints whose upstream response shape breaks the bridge). Codifies that `ext-*` skills document substitutes in §3 rather than silently falling back, and that substitutes are verified by live-fire, not derived from documentation.
- **`last_verified` is the only freshness signal for `ext-*` recordings** — Records the deliberate non-adoption of periodic CI smoke tests in favor of a date stamp on each recording, and the resulting agent obligation to bump the date on every re-verify. Crystallizes the trade-off (a recording's staleness becomes a visible audit signal rather than a CI gate that costs minutes every push).
