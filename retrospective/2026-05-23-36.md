## Part 1 — what happened

### Phase 1A — Cold phase-1 bring-up against live sandbox (#34)

Goal: drive `apply-and-verify` for the management module from "code complete, never applied" to "ArgoCD UI returns HTTP 200 over HTTPS through the NLB." Plan was 1–2 strikes; reality was 6 fix attempts plus a 7th that landed clean.

The seven distinct bug classes (in order encountered):

1. **EKS v20 default flip** — `enable_cluster_creator_admin_permissions` defaults to `false` in v20. The IAM principal that creates the cluster gets no access entry, so the helm provider's first call back to the API server returns `the server has asked for the client to provide credentials`. Diagnosis took an apply cycle (~15 min) because the symptom appeared mid-apply, after EKS had built.
2. **RBAC propagation race on first helm release** — access entry created at apply start, but the in-cluster RBAC binding propagated unevenly. Two of three parallel helm releases succeeded; ingress-nginx (started simultaneously) got a `serviceaccounts is forbidden` on its first call. A pure retry resolved it; could not deterministically test for.
3. **ArgoCD IRSA on the wrong ServiceAccount** — chart 6.7.3 has per-component SAs; we set `serviceAccount.annotations` (top-level, unused) instead of `server.serviceAccount.annotations`. Silent — the apply succeeded, but the e2e verify step caught it.
4. **ExternalDNS install completely missing from helm.tf** — `module.irsa_external_dns` existed in `irsa.tf` but no `helm_release` consumed it. The argocd-server ingress annotation was reconciled by nothing, so DNS never appeared. The longest-living silent bug.
5. **bitnami external-dns chart misconfigured** — first attempt at adding ExternalDNS used `bitnami/external-dns 6.31.0`, which timed out at 5 min with pods not Ready. Switched to upstream `kubernetes-sigs/external-dns` 1.15.0 with simpler values structure. User then said "stay away from bitnami for everything" — adopted as policy.
6. **ExternalDNS IRSA policy missing `route53:ListHostedZones`** — the policy had `ListHostedZonesByName` only. ExternalDNS started fine, then every reconcile loop logged `AccessDenied`. Caught only after I added pod-log dumps to the failure path in the e2e step.
7. **ArgoCD ingress key drift: `hosts[0]` vs `hostname`** — `server.ingress.hosts[0]` was a silent no-op; the chart wants `server.ingress.hostname` (singular). The rendered ingress carried `argocd.example.com` (chart default) until I caught it via the new diagnostic dump.

After 7, phase 1 went green: all verify checks passed including the HTTP 200 over HTTPS.

### Phase 1B — Test scaffolding (#34, continued)

The user's lesson from the seven strikes: **"the cycle time is so long you need to test as many aspects as you can of your implementation at the same time."** Shipped four layers in one PR:

- **`tests/unit/`** — `test_helm_render.sh` (asserts contracts the chart helms produce), `test_irsa_helm_linkage.sh` (every IRSA module is referenced by a helm_release), `test_iam_required_actions.sh` (per-component IAM action allowlist, fixture-driven), `test_eks_module_defaults.sh` (trip-wire flags must be explicit in `eks.tf`). Five of the seven strikes would have been caught by these at authoring time, in <30s with no AWS access.
- **`policies/audit/`** — Kyverno installed in Audit mode plus eight starter ClusterPolicies. Continuous in-cluster assertion store; catches drift from any source (chart bump, Argo sync, hand-edit).
- **`tests/integration/`** — Ten end-to-end smoke tests, each exercising one component (ArgoCD app sync, ExternalDNS → Route53, NLB → nginx → echo HTTP round-trip, ESO secret round-trip, raw Crossplane MR, XRD/Composition/Claim, Kyverno PolicyReport, IRSA STS round-trip, second ingress, GitOps loop).
- **`scripts/`** — Eight read-only deterministic diagnostic helpers (`k8s-status`, `diag-component`, `kyverno-violations`, etc.), so the next session has a baseline of in-cluster introspection ready to go.
- **`ai/TESTING-PLAN.md`** — Four-layer testing strategy with bug-to-test traceability matrix; Chainsaw planned for phase 2 (Crossplane logic).

## Part 4 — proposed ADRs

Architectural decisions made in this session that the user may want to record as ADRs. Titles only — no specs. Use the `adr` skill to author any of these if you decide they're worth recording.

- **No bitnami charts in the platform stack** — user-stated policy after the external-dns 6.31.0 failure. Currently encoded only in commit messages and §6.4 context; would benefit from a single durable rationale doc.
- **CLAUDE.md is a pointer; AGENTS.md is canonical** — the cross-agent convention adopted in PR #35. Affects every future agent-instructions edit.
- **Four-layer testing strategy (unit + Kyverno + integration + Chainsaw)** — codified in `ai/TESTING-PLAN.md` but never formally adopted as an ADR. Worth recording because phase-2 onward must choose which layers apply to each new artifact.
- **TDD on bug fix is a hard rule, not a guideline** — `AGENTS.md §6.2` is currently written as procedure; an ADR would record the *rationale* (the asymmetry between cost of writing the test and cost of missing the regression) so future agents can argue with the *principle* rather than the *procedure*.
- **Wait=false for charts whose readiness is testable end-to-end** — adopted for ExternalDNS and Kyverno after bitnami stuck for 5 min on wait=true. Decision affects every new helm_release.
- **Stacked PRs as the default workflow for multi-step changes** — used three times in this session; mechanics described informally in `AGENTS.md §3` but no rationale doc.
