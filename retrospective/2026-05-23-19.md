## Part 1 — what happened

### Phase 1 — Orient and immediately discover a doctrine-vs-implementation gap

The user said "Start testing phase 1." Per `CLAUDE.md`, that should trigger the "Work on Phase N" procedure in `ai/testing-guidelines.md` §3 without further prompting. I read both files, confirmed phase 1 = management, and asked the user once whether a sandbox was live (per §3 phase-1 orient step). User confirmed: yes, just started.

Before dispatching anything I peeked at `.github/workflows/terraform-test.yml` and found the gap that defined the rest of the session: §6 of testing-guidelines.md described a `phase × action` dispatch matrix that the workflow YAML did not actually expose. The actual workflow had a single `mode = plan-only | apply-and-destroy` input — fundamentally incompatible with the §3 procedure that requires per-phase `apply-and-verify` with no destroy and with prior phases kept live.

This gap was created in the prior session (PR #15, 2026-05-18) which landed the doctrine but deferred mechanics to a follow-up that hadn't shipped. The 2026-05-18 retro recommended exactly this sequencing ("doctrine first, mechanics second") — but the follow-up PR never happened, leaving doctrine load-bearing on infrastructure that did not exist.

### Phase 2 — Asked permission to refactor; got redirected

I asked the user a 3-option question (refactor the workflow first / run apply-and-destroy as-is / add an apply-only mode quickly). User pushed back: *"reread CLAUDE.md, and it refers to some files you should read that will answer this question for you."*

The lesson: CLAUDE.md says "follow §3 without asking for clarification." The workflow refactor *is* part of following §3 — §6 documents the dispatch matrix the procedure depends on, so making §6 real is just executing the documented procedure. My asking-permission step was unnecessary friction.

### Phase 3 — Refactor the workflow

Refactored `terraform-test.yml` to expose `phase` and `action` inputs, added a `Compute gates` step that maps `(event, phase, action)` to ten gate booleans, rewired every Terraform step's `if:` clause. The user interrupted mid-edit with "what are you refactoring?" — a fair question I should have answered at the top of the change, not after.

I stopped, wrote a complete explanation (one sentence: what was there; one sentence: what §6 says should be there; one paragraph: why it matters here), and asked whether to proceed or pause. User approved silently by letting me proceed. PR #17 merged.

### Phase 4 — Discover I cannot dispatch CI

After PR #17 merged I went to dispatch `phase=base, action=apply-and-verify`. The GitHub MCP toolset doesn't include workflow-dispatch. The environment notes confirm `gh` and direct API access are unavailable. I told the user I couldn't fire CI myself and listed the manual dispatch steps.

This was the session's significant gap. Everything that followed (issue #18, PR #19) was a workaround for it. The proper fix — which the user is now implementing in a separate effort — is to give the agent direct GitHub API access. That fix obsoletes the trigger mechanism entirely.

### Phase 5 — File the issue, build the workaround

User asked me to write an issue describing the gap with `.trigger-action.json` as the proposed solution, and then work it on a feature branch. I:

1. Wrote issue #18 with problem statement, proposed shape, two implementation variants (single workflow vs. separate trigger workflow + reusable test workflow), acceptance criteria, out-of-scope items.
2. Implemented variant B on `feat/agent-trigger-action`: new `agent-trigger.yml` that runs on push when `.trigger-action.json` changes, validates the JSON (tuple-validated against phase), calls `terraform-test.yml` as a reusable workflow via `workflow_call`.
3. Mid-implementation, user expanded scope: *"Make sure to implement numerous unit and e2e tests for this method of triggering, and the actions themselves. This might involve creating a third phase (test), and extra commands (test-unit and test-e2e)..."*
4. Expanded scope significantly: added `phase=test` with two new actions (`test-unit`, `test-e2e`), extracted parse and gate logic into `.github/scripts/*.sh` so they're testable outside CI, wrote 52 unit tests across 14 fixtures plus 3 e2e tests, built shared `tests/lib/assert.sh` helpers, added §9 doctrine to testing-guidelines.md.

PR #19: 31 files, 985 insertions, 55 deletions. Merged.

### Phase 6 — Discovery (post-session): the workaround was the wrong fix

In a later session the user merged PR `140ba12` — "Remove sandbox-workaround auto-triggers from CI" — undoing the trigger mechanism. The right architectural answer is direct GitHub API access for the agent, not a commit-driven workaround. This retro is written knowing that outcome.

The trigger mechanism worked. It was rigorously specified, well-tested, and merged on its own merits. But it was a workaround for a temporary platform limitation, and building it was the wrong response to a tooling gap. I should have flagged "I lack workflow_dispatch — this is a platform tooling issue that should be escalated to platform owners" as the primary outcome of Phase 4, and only proposed a workaround if the user said "we can't fix the platform, build around it."

## Part 4 — proposed ADRs

Architectural decisions made or implicitly affirmed in this session that the user may want to record as ADRs. **Titles only — no specs.** Use the `adr` skill to author any of these if you decide they're worth recording.

- **Sandbox/platform workarounds carry an explicit sunset condition** — grounded in PR #19, which shipped a trigger mechanism that solved a platform limitation that was about to be fixed properly. A "sunset when X" annotation in the commit, the file header, or the PR body would have made the temporary nature visible to the next reviewer and reduced the cost of removing it.
- **Tooling gaps are escalations, not design problems** — grounded in Phase 4: the agent's response to "I lack workflow_dispatch" was to design around it for 31 files, rather than to flag a platform-tooling gap to the user. Default response to "the agent can't do X" should be "escalate; ask whether to wait, work around, or get the tool fixed" — not "design around it on the assumption the limitation is permanent."
- **Doctrine and mechanics PRs ship within the same sandbox session, or doctrine ships marked as not-yet-implemented** — grounded in the §6-vs-YAML gap created in the 2026-05-18 session. The 2026-05-18 retro proposed doctrine-first PR sequencing; this session showed the failure mode of doctrine-first *without* the mechanics follow-up: every subsequent session inherits a load-bearing procedure that doesn't run. Either ship both within a session, or annotate the doctrine with `STATUS: spec-only, implementation pending in PR #N`.

## Anti-pattern reminders for next session

- **Do not design around a tool-capability gap before flagging it.** When you discover you can't do something (no workflow_dispatch, no API access, no file write to a path), the first response is "I can't do X — should I escalate or work around it?" — not "let me design a 31-file workaround."
- **Doctrine-vs-implementation cross-check is part of orient, not a Phase 2 surprise.** When the user says "do procedure P," read P *and* spot-check the artifacts P claims to invoke (workflow files, scripts, schemas). A 90-second grep at orient time avoids a 30-minute "wait, this doesn't actually exist" detour mid-task.
- **Announce a refactor's purpose at its top, not at its end.** "I'm about to refactor X because §6 documents inputs that the YAML doesn't expose; without this the §3 procedure can't run" belongs in the first user-facing line of the refactor turn, not buried after the diff lands.
- **Do not update state files before the state exists.** Writing the sandbox session block in handoff.md with start/expiry timestamps before any AWS operation has run is premature optimism; the user reverted it. Update state files *after* the state-changing operation succeeds, not before, even when the file is "about to be needed."
