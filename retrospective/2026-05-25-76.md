## Part 1 — what happened

### Phase 1 — Compact session / hook outage

The session started as a compact continuation from a prior context window. The `SessionStart` hook correctly created `/tmp/agents-md-unread`, but the `PostToolUse` hook that should clear it on AGENTS.md reads received empty stdin — making `jq -r '.tool_input.file_path'` return null, so the case pattern never matched and the flag was never cleared. The result was that every non-Read tool call (Bash, Write, Edit, Agent) was blocked for the entire first half of the session. The only tools available were Read, AskUserQuestion, and ToolSearch.

The session spent roughly an hour in this state: reading the hook config to diagnose the root cause, composing handoff content via chat messages (not Write calls), and waiting for the user to either run `rm /tmp/agents-md-unread` or switch machines. The eventual resolution was the user restarting on a fresh machine (`/home/jmanton/src/lago-morph/k8-platform`) where the hook state was clean.

The fix for the hook is a one-line guard: `jq -r '.tool_input.file_path // empty'` plus an early exit when the result is empty string. Documented in the handoff and as AGENTS rule `d3e613df02`.

### Phase 2 — Crossplane 2.3.0 upgrade (PR #74)

The work for this phase was largely authored in the prior context window and only the final diagnosis + hook-unblocking happened in this session. The upgrade from 2.0.1 to 2.3.0 encountered three cascading bugs:

**Bug 1 — `forceOverwriteReplica: true` rejected by SSA strict schema.** Crossplane 2.3's composite reconciler uses Server-Side Apply and enforces strict field validation. The `crossplane/compositions/platform-secret.yaml` had `forceOverwriteReplica: true` in the ASM Secret base — a field that `provider-aws-secretsmanager`'s CRD does not declare. v2.0.1's reconciler tolerated it; v2.3 rejected it with `field not declared in schema`. Fix: remove the field.

**Bug 2 — Crossplane SA has no RBAC for `externalsecrets.external-secrets.io`.** Crossplane 2.3's composite reconciler enforces RBAC strictly when applying composed resources. The PlatformSecret Composition renders an `ExternalSecret` (an ESO CRD, not a Crossplane provider CRD). Crossplane has no auto-RBAC for non-provider kinds. Without an explicit grant, the reconciler logged `crossplane-system:crossplane is not allowed to [get list watch create update patch delete] externalsecrets`. Fix: create `crossplane/rbac/01-crossplane-externalsecrets.yaml`, wire into ArgoCD include filter and chainsaw run.sh.

**Bug 3 (open) — provider-family-aws v1.12.0 slow under Crossplane 2.3.0.** Even with Bugs 1 and 2 fixed, chainsaw scenarios time out at 245s. The `CreatedExternalResource` event on the ASM Secret MR appears at t+2m9s (expected ~10s on 2.0.1). ESO gives up at t+3m27s. The Crossplane controller log confirms all three beta flags are disabled; the delay appears to be in the provider's internal reconcile queue under the new core reconciler. Hypothesis: v1.12.0 was authored against the 2.0.x model; bumping to latest v1.x may resolve. Not fixed this session.

One additional bug was in the beta-feature disable flags themselves: the flag for SSA claims was initially written as `--enable-claim-ssa=false` (unknown flag, caused crashloop and helm 5-minute timeout). The correct flag name from Crossplane 2.3.1 source (`core.go`, field `EnableSSAClaims`) is `--enable-ssa-claims=false`. Fixed in commit `de6132c`.

### Phase 3 — Session-wrap mishap

When writing the handoff update, the commit was made directly to `main` instead of a branch. This violates AGENTS.md §3. The fix required `git checkout -b chore/handoff-2026-05-25` followed by `git checkout main && git reset --hard origin/main`, then pushing the branch and opening PR #76. Total cost: ~10 minutes of unwind. The failure mode is subtle: at session wrap, the mental model is "just update docs", which feels like it shouldn't need a branch — but it absolutely does.

## Part 3 — agents-file suggestions

Proposed additions to `AGENTS.md`. Each rule has its own per-rule file in
`./2026-05-25-76/AGENTS-MD-<hash>-<name>.md`. This section mirrors both the
instruction and justification inline for review-decision convenience.

### Suggestion 1: Git branch before any session-wrap commit — `AGENTS-MD-a4c9620c57`

- **Per-rule file**: [./2026-05-25-76/AGENTS-MD-a4c9620c57-git-branch-before-session-wrap.md](./2026-05-25-76/AGENTS-MD-a4c9620c57-git-branch-before-session-wrap.md)

**Proposed agent instruction:**

> **Git branch before any session-wrap commit.** Any commit made at session wrap (handoff update, retrospective, chore) must land on a named branch, not `main`. Create the branch first (`git checkout -b chore/<name>`), make the commit, push, and open a PR.
>
> *Grounded in: 2026-05-25 session handoff committed directly to main, requiring a 10-minute checkout-b/reset-hard unwind.*

**Justification:**

At session wrap the mental model is "just updating docs" — it feels like it shouldn't need a branch. But it violates AGENTS.md §3 and requires a non-trivial unwind (checkout -b, reset --hard origin/main, push branch, open PR) that costs the next session roughly 10 minutes. The marginal cost of creating a branch first is one command. The asymmetry is stark: one `git checkout -b` saves a three-step recovery at the start of the next session.

### Suggestion 2: PostToolUse hook compact-session stdin guard — `AGENTS-MD-d3e613df02`

- **Per-rule file**: [./2026-05-25-76/AGENTS-MD-d3e613df02-posttooluse-hook-compact-session-stdin-guard.md](./2026-05-25-76/AGENTS-MD-d3e613df02-posttooluse-hook-compact-session-stdin-guard.md)

**Proposed agent instruction:**

> **PostToolUse hook compact-session stdin guard.** When authoring a `PostToolUse` hook that reads `tool_input.file_path` from stdin via `jq`, guard against null: use `jq -r '.tool_input.file_path // empty'` and `exit 0` immediately if the result is empty string. Compact/resumed Claude Code sessions may deliver empty or unparseable stdin to the hook, causing `jq` to return null and any `case` match to fail silently — leaving the flag in place and blocking all non-Read tool calls for the entire session.
>
> *Grounded in: 2026-05-25 session — hook blocked all Bash/Write/Edit calls for ~1 hour until machine switch.*

**Justification:**

The existing `PostToolUse` hook used `jq -r '.tool_input.file_path'` without a null fallback. In a compact session the stdin payload was empty or differently structured, so `jq` returned the literal string `null`, the `case "$FP" in */AGENTS.md)` pattern didn't match, and the `/tmp/agents-md-unread` flag was never cleared. The entire session was spent in Read-only mode, unable to use Bash, Write, or Edit — roughly 1 hour of dead time. The fix is one extra `// empty` in the jq expression plus an early exit: `[ -z "$FP" ] && exit 0`. Adopting this rule costs one tool call at hook authoring time; failing to have it costs an entire session.

### Suggestion 3: Crossplane beta flags must be identical in management and chainsaw — `AGENTS-MD-a4f7c59f15`

- **Per-rule file**: [./2026-05-25-76/AGENTS-MD-a4f7c59f15-crossplane-beta-flags-parity.md](./2026-05-25-76/AGENTS-MD-a4f7c59f15-crossplane-beta-flags-parity.md)

**Proposed agent instruction:**

> **Crossplane beta flags must be identical in management and chainsaw.** When disabling Crossplane beta features for a version bump, apply the identical `--enable-X=false` args in BOTH `terraform/management/helm.tf` (the live EKS cluster) AND `tests/chainsaw/run.sh` (the kind cluster). Drift between the two silently invalidates chainsaw as a proxy for production — scenarios pass on kind because a beta feature is on there but off on EKS (or vice versa).
>
> *Grounded in: PR #74 — three beta flags added to helm.tf and run.sh in the same commit to enforce parity.*

**Justification:**

The chainsaw harness is the fast proxy for production Crossplane behavior. If the kind cluster runs with different feature flags than the EKS management cluster, a green chainsaw run is meaningless — it tested different code paths. The 2.3.0 upgrade involved three beta-feature disables. Had they been applied only to helm.tf and not run.sh, chainsaw would have reported green on a configuration that would fail on EKS. The unit test `test_chainsaw_crossplane_matches_management.sh` already enforces version parity; the same logic should extend to flag parity. Marginal cost: one glance at run.sh when editing helm.tf.

### Suggestion 4: Verify push succeeds before declaring work done — `AGENTS-MD-6f09a9aa26`

- **Per-rule file**: [./2026-05-25-76/AGENTS-MD-6f09a9aa26-verify-push-before-done.md](./2026-05-25-76/AGENTS-MD-6f09a9aa26-verify-push-before-done.md)

**Proposed agent instruction:**

> **Verify push succeeds before declaring work done.** After `git commit`, always confirm `git push` exits 0 and the remote shows the commit. A local commit with no successful push is indistinguishable from "not done" to any subsequent session or CI run. If push fails (SSH key unavailable, upstream diverged), surface the failure immediately — do not declare the session complete while the commit is local-only.
>
> *Grounded in: 2026-05-25 session — handoff commit `b498d1f` was local-only on main for an extended period after the push failed with SSH key error.*

**Justification:**

During session wrap, `git push origin main` failed with `Permission denied (publickey)`. The commit existed locally but was never visible to GitHub or the next session. The fallback push attempt via HTTPS also failed. The result was a local-only commit that appeared done from inside the session but was invisible externally. The fix costs one `git log --oneline origin/main..HEAD` check after every push to confirm the branch advanced on the remote.

### Suggestion 5: Crossplane beta flag names must be verified from source before use — `AGENTS-MD-4350c4c1b2`

- **Per-rule file**: [./2026-05-25-76/AGENTS-MD-4350c4c1b2-crossplane-beta-flag-name-verification.md](./2026-05-25-76/AGENTS-MD-4350c4c1b2-crossplane-beta-flag-name-verification.md)

**Proposed agent instruction:**

> **Crossplane beta flag names must be verified from source before use.** When disabling a Crossplane feature flag, look up the exact CLI flag name from the Crossplane source (`core.go` or the equivalent for the target version) or the release notes before writing it into helm.tf or run.sh. Do not guess from the field name in the Crossplane feature-gate struct — the struct field name (`EnableSSAClaims`) does not always map to the CLI flag name (`--enable-ssa-claims`) in an obvious way, and an unknown flag causes a crashloop that triggers helm's 5-minute timeout.
>
> *Grounded in: PR #74 commit `de6132c` — initial flag `--enable-claim-ssa=false` caused crossplane pod crashloop; correct flag is `--enable-ssa-claims=false` from core.go.*

**Justification:**

The initial attempt used `--enable-claim-ssa=false` derived by guessing from the struct field name. Crossplane rejected it as an unknown flag, entered a crashloop, and helm waited the full 5-minute timeout before failing. The correct flag from Crossplane v2.3.1 `core.go` is `--enable-ssa-claims=false`. The cost of the wrong flag was ~7 minutes per CI run plus multiple debug cycles. The cost of the right behavior is one `grep -r EnableSSAClaims crossplane/pkg` or a scan of the `--help` output before writing the flag.
