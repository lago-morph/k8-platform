## Part 1 — what happened

### Phase 1 — Read the canon, identify the gap

The session opened with the user noting that `ext-github` (merged earlier the same day as PR #30) is now an active capability. The brief was open-ended: "look at the current plan and other handoff type documents, and figure out how that changes the instructions you give to yourself during various situations."

I read `CLAUDE.md`, `ai/handoff.md`, `ai/testing-guidelines.md`, the `ext-github` SKILL.md, the design spec at `ai/specs/ext-github-design.md`, and the existing `terraform-ci-watch` skill + its reference docs. The gap was immediate: `terraform-ci-watch/SKILL.md`, `reference/log-fetching.md`, and `reference/escalation-template.md` were all written around `gh` CLI commands (`gh api`, `gh run view --log-failed`), with "GitHub MCP tools" listed as a fallback. Neither path works in the Claude Code on the Web sandbox — `gh` is absent and the attached GitHub MCP server does not cover the Actions API. The terraform-ci-watch loop, which the project's CLAUDE.md instructs to invoke after every push, was effectively un-runnable as written.

### Phase 2 — First commit (89a9884): rewire to ext-github

I rewrote SKILL.md's Phases 1, 2, and 4 around `ext-github` operations directly: `list_workflow_runs` for locating runs, the single-run-GET catalog-gap substitute for polling, `list_jobs_for_workflow_run` + `download_job_logs` for failure logs. The `reference/log-fetching.md` rewrite stripped the four `gh` / MCP fallback options and made the `ext-github` per-job path the primary (and only) approach. `CLAUDE.md` and `ai/testing-guidelines.md` got short additions saying "no `gh` in this sandbox; `ext-github` is the only path."

Pushed, opened PR #32 as draft, subscribed to webhook activity. Mid-work the system reminded me "You do NOT have access to the gh tool" — which I treated as confirmation of the design I'd already shipped. (In hindsight that reminder should have caused me to ask the wider question, not just relax into "good, I'm on the right track.")

### Phase 3 — User catch: "I use a lot of different sandbox types"

The user reviewed the draft PR and replied:

> "Before we commit these, we need to consider that I use a lot of different sandbox types. Some may have gh access. Some may have less-restrictive GitHub MCP servers. Some might even block the path using the Jentic MCP server. So the question is, how can we make this so that it works NOW, but can adapt later."

That was the catch. I had written instructions for *this* sandbox and called them universal. The user — who runs the same skill in workstations, Codespaces, and other web-sandbox configurations — was about to inherit a single-environment doc dressed up as project guidance.

I owned the gap, surfaced the variability surface (three independent dimensions: `gh` presence, GitHub MCP Actions coverage, jentic reachability), and proposed two designs:

- **Option A:** profile detection + operation×profile dispatch table. One detection at start, abstract operations everywhere.
- **Option B:** preference-ordered inline fallback in each phase.

Recommended A; the user chose A and pinned the preference order: **`gh` CLI → GitHub MCP server with Actions coverage → `ext-github` via jentic**.

### Phase 4 — Second commit (acbe1eb): the rework

New file: `terraform-ci-watch/reference/capabilities.md`. Four sections:

- **§1 detection sequence** — first hit wins; for `github-mcp`, require *all five* Actions-API operations to be covered before claiming the profile (partial coverage is worse than the next profile down).
- **§2 operation×profile dispatch table** — five abstract operations (LOCATE_RUN, POLL_RUN, LIST_FAILED_JOBS, FETCH_JOB_LOG, DISPATCH) with per-profile implementations.
- **§3 mid-loop degradation** — on connectivity failure, re-detect once; never ping-pong.
- **§4 concurrency precondition** — every profile must enforce the `>2 queued` refuse-and-report gate around DISPATCH, since `terraform-test.yml` has `cancel-in-progress: false`.

Rewrote SKILL.md to reference abstract operation names and defer resolution to `capabilities.md`. The "no `gh` in sandbox" framing — load-bearing in commit 1 — disappeared entirely; profile detection runs before Phase 1 and the rest of the skill is portable. `log-fetching.md` got the same treatment. `escalation-template.md`'s one `gh` line became "call LIST_FAILED_JOBS per `capabilities.md` §2". `CLAUDE.md` and `ai/testing-guidelines.md` (both §3 and §9) lost the "ext-github is the sole path" framing and gained pointers to `capabilities.md`.

Before committing, ran a cross-file `grep` for operation names (LOCATE_RUN, POLL_RUN, LIST_FAILED_JOBS, FETCH_JOB_LOG, DISPATCH) and profile names (`gh`, `github-mcp`, `ext-github`) across the six files to catch drift. No typos surfaced; all operation references resolved against `capabilities.md`. Cross-references to `ext-github` §3.1, §3.2, §5 and to `ai/testing-guidelines.md` §9 also verified.

Pushed; PR #32 merged via webhook a few minutes later. Auto-unsubscribed.

## Part 4 — proposed ADRs

Architectural decisions made in this session that the user may want to record as ADRs. **Titles only — no specs.** Use the `adr` skill to author any of these if you decide they're worth recording.

- **Capability profile dispatch as the standard pattern for environment-variable skills** — codifies that skills depending on external APIs/CLIs/MCP servers should detect+dispatch rather than hardcode the current environment. Grounded in: PR #32's commit 1 → commit 2 pivot.
- **Preference order for GitHub API transports: `gh` → GitHub MCP → `ext-github`** — locks the ranking in writing. The order was decided verbally during PR #32 and is now baked into `capabilities.md`; an ADR would make the rationale (latency, broker dependency, credential surface area) reviewable.
- **Per-job logs as the universal log-fetch unit, not run-wide logs** — adopted to avoid the 302-redirect class of failure where `gh` follows, MCP varies, and jentic 500s. Cross-cutting design rule that applies beyond `terraform-ci-watch`.
