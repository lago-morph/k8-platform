## Part 3 — agents-file suggestions

### Suggestion 1: Verify the current branch before every commit when background worktree subagents run — `AGENTS-MD-6487010aa8`

- **Per-rule file**: [./2026-06-08-207/AGENTS-MD-6487010aa8-verify-branch-before-commit-with-worktree-subagents.md](./2026-06-08-207/AGENTS-MD-6487010aa8-verify-branch-before-commit-with-worktree-subagents.md)

**Proposed agent instruction:**

> **Verify the current branch before every commit when background worktree subagents run.** "When any background subagent is running in an isolated worktree, ALWAYS run `git branch --show-current` immediately before each `git add`/`git commit` in your main worktree — a subagent's `git checkout -B <branch>` can move the MAIN worktree's HEAD, silently landing your commit on the wrong branch."
>
> *Grounded in: auto-015, where a P5 worktree subagent's checkout moved the main HEAD and the OI-1 impl commit landed on the wrong branch, requiring a cherry-pick recovery.*

**Justification:** In auto-015 a worktree subagent's `git checkout -B` moved the main HEAD; the lead authored the entire OI-1 impl believing it was on the OI-1 branch, then pushed the OI-1 branch with only the brief commits. It surfaced only when a terraform apply reported "No changes" (the policy diff was on the wrong branch), forcing a ~20-minute forensic cherry-pick recovery and risking an empty PR. The rule costs one `git branch --show-current` per commit — turning a silent, expensive error class into an immediate catch.

### Suggestion 2: Do not trust `simulate-principal-policy` for resource-scoped IAM create deny tests — `AGENTS-MD-aa74b8db39`

- **Per-rule file**: [./2026-06-08-207/AGENTS-MD-aa74b8db39-simulate-principal-policy-unreliable-for-create.md](./2026-06-08-207/AGENTS-MD-aa74b8db39-simulate-principal-policy-unreliable-for-create.md)

**Proposed agent instruction:**

> **Do not trust `simulate-principal-policy` for resource-scoped IAM create deny tests.** "Do NOT use `aws iam simulate-principal-policy` as the firing proof for a resource-scoped IAM narrowing (e.g. `iam:CreateRole` on `role/<prefix>-*`): on a freshly-modified IRSA role it returns `implicitDeny` for EVERY action — even unambiguously-allowed `Resource:"*"` ones — so it cannot distinguish allow from deny. Prove the narrowing on the live CREATE path (drive the real controller to create a resource the policy must permit) plus a static source lint, and make any simulate-based check SKIP (never FAIL) when its in-scope positive control is itself denied."
>
> *Grounded in: auto-015, where the simulate-based IAM deny check returned implicitDeny for `eks:DescribeCluster` (a `Resource:"*"` allow), proving the simulator unusable on the just-narrowed role.*

**Justification:** auto-015's deny check, run against the freshly-modified crossplane role, returned `implicitDeny` for every probe including `eks:DescribeCluster` (which the role allows on `*`). The policy was verified correct and the real IAM engine permitted the in-scope creates moments later — so the simulator, not the policy, was wrong. Trusting it yields a false FAIL or a meaningless PASS. The rule costs nothing: redirect the firing proof to the live CREATE path (the authoritative real-engine test anyway) and a static lint, and self-disable the simulate check when its positive control is denied.

### Suggestion 3: Hold a live-policy-mutating PR as a sentinel-gated draft until validated on a CREATE path — `AGENTS-MD-95ceb91b7a`

- **Per-rule file**: [./2026-06-08-207/AGENTS-MD-95ceb91b7a-sentinel-gated-draft-for-live-policy-prs.md](./2026-06-08-207/AGENTS-MD-95ceb91b7a-sentinel-gated-draft-for-live-policy-prs.md)

**Proposed agent instruction:**

> **Hold a live-policy-mutating PR as a sentinel-gated draft until validated on a CREATE path.** "A PR that mutates a LIVE cloud IAM/policy applied from a branch before merge must open as a DRAFT carrying a failing required check (a committed sentinel-file gate) that stays RED until a session OBSERVES the tightened policy working on a real CREATE path; clear it by committing the sentinel — with the validating run-id — ATOMICALLY with the open-issue RESOLVED flip and the handoff record. Never rely on a prose 'do not merge' note."
>
> *Grounded in: auto-015 OI-2026-06-08-1, where the IAM narrowing shipped as a draft + `test_iam_tightening_gate.sh` sentinel and was un-drafted only after the spoke CREATE-path validation was observed.*

**Justification:** A live-policy change applied from a branch before merge creates a window where a prose "do not merge" note is unenforceable — a bottom-up reviewer merges a green-looking PR by reflex. auto-015 made the hold machine-enforced (draft + a unit test red until a sentinel is committed) and cleared it only after observing the create-path validation, atomically with the issue flip + the run-id record. ~30 lines of gate test vs. an unvalidated live-policy change merged by mistake with a slow-to-surface blast radius.

### Suggestion 4: Overlap long live-provisioning waits with cluster-independent authoring and review — `AGENTS-MD-ad5c8f495d`

- **Per-rule file**: [./2026-06-08-207/AGENTS-MD-ad5c8f495d-overlap-provisioning-waits-with-authoring.md](./2026-06-08-207/AGENTS-MD-ad5c8f495d-overlap-provisioning-waits-with-authoring.md)

**Proposed agent instruction:**

> **Overlap long live-provisioning waits with cluster-independent authoring and review.** "When a step blocks on slow live provisioning (an EKS bring-up is ~20-30 min), do NOT idle — dispatch the cluster-independent code authoring (test harnesses, scripts) and the decision-brief adversarial-review subagents to run during the wait, then do the live validation once the substrate is up."
>
> *Grounded in: auto-015, where P3/P4/P5 authoring and the 6 OI-1 adversarial reviewers ran during the base/management/spoke EKS provisioning waits.*

**Justification:** auto-015's critical path was three serial ~20-30 min EKS provisions. Filling those waits with the P3/P4/P5 authoring + two rounds of adversarial review meant most code and all decision review were done by the time the substrate was up, leaving the live window for validation only. The marginal cost is tracking the in-flight run-ids; the cost of not doing it is idling through an hour of provisioning — the difference between a run that ships a handful of PRs and one that ships a stack.
