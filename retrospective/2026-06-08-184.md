## Part 1 — what happened

### Phase 1 — The spike: SSM vs NLB, decided by one unknown

The task was to give the sandbox direct `kubectl` against EKS, blocked because the
egress gateway only trusts public certs and EKS serves a private-CA cert. Two finalists:
an SSM port-forward tunnel or an NLB with a public ACM cert. The whole choice hinged on
one unknown — does the gateway sustain the SSM `ssmmessages` websocket? Rather than build
either, a throwaway t3.micro was stood up and a port-forward + `curl` run through it:
`HTTP=200 ssl_verify=0` with the real body. That proved the gateway permits the websocket
AND that kubectl gets real end-to-end TLS / real cluster-CA verification through the
tunnel — settling SSM (no public listener, real CA) over NLB in minutes.

### Phase 2 — Build the substrate + author, in parallel

Account was ephemeral and empty, so base + management were brought up via CI
(`terraform-test.yml apply-and-verify`) while the hub Terraform, Composition wiring, and
helper script were authored. Recon was delegated to two haiku subagents; authoring stayed
on the lead. The hub got an SSM relay + a read-only EKS access entry; the Composition got
the same per cluster.

### Phase 3 — Two owner-driven design pivots

The owner asked whether instances were really needed (they are — SSM needs a managed
target) and then surfaced a hard constraint: the account is capped at 9 EC2 instances, a
10th closes it. That collapsed "a relay per cluster" into ONE shared relay in the base
VPC, with each cluster admitting it via a security-group ingress rule — per-spoke cost
became zero new instances.

### Phase 4 — Behavioral verification found two invisible-to-lint bugs

Driving the real Composition on a second live cluster (the hub path already worked) is
where ADR-0006 earned its keep. The relay-ingress MR (`SecurityGroupIngressRule`) never
synced — `provider-aws-ec2 v2.5.0` can't observe it ("Missing Resource Identity After
Read", terraform-provider-aws#45303). Switched to the classic `SecurityGroupRule`. Then
it failed create with `UnauthorizedOperation` — the crossplane IRSA role lacked
`ec2:AuthorizeSecurityGroupIngress`. Both were fixed and re-verified; both were invisible
to render goldens and `yq`/`grep`.

### Phase 5 — The tax: stale branch, ADR collisions, a flaky gate

A lot of unrelated friction surfaced. The working branch was 4 commits behind `main`
(the sandbox clones once at container start), so a subagent's ADR landed as `0006` (taken)
then `0007` (taken in an open PR) — two collisions, owner corrections, a rename. The
chainsaw gate went red 3× on the pre-existing OI-2026-05-28-1 ASM-deletion flake, and the
reflex was to re-kick and rationalize — which the owner rightly called the disease. A
`CHAINSAW_INCLUDE_REALAWS`/nightly lane was found shunting real behavioral tests off the
gate. The account then timed out, making clean-build validation impossible this session.

### Phase 6 — Turn the pain into durable guardrails

The session's tail converted the friction into rules and a plan: AGENTS §6.34
(build-coupled verification → ADR-0006), §6.35 (never "done" on a manually-modified
build), §6.36 (a red gate is real; no nightly/non-gating; determinism or delete);
`docs/decisions/0008` (the tool, scoped implementation-only); a reopened OI-2026-06-06-4
+ the OI-2026-05-28-1 deterministic-poll fix plan; and an explicit
`docs/testing-debt-burndown.md` with a NEXT-SESSION run order. Critically, #184 was
relabeled **NOT done** — its spoke proof ran on a manually-modified build (paused
auto-sync + hand-applied manifests), which §6.35 says is mechanism-proof, not done.

## Part 3 — agents-file suggestions

Each rule has a per-rule file in the sibling directory (`# agent instruction` +
`# justification`). Three of these (clean-build, red-gate, build-coupled) were also added
inline to `AGENTS.md` on PR #184 as §6.34/§6.35/§6.36 at the owner's direction — the
per-rule files are the canonical pipeline form; **dedupe at assembly time** so they land
once.

### Suggestion 1: Never mark work done on a manually-modified build — `AGENTS-MD-b6ca8d3a22`

- **Per-rule file**: [./2026-06-08-184/AGENTS-MD-b6ca8d3a22-clean-build-before-done.md](./2026-06-08-184/AGENTS-MD-b6ca8d3a22-clean-build-before-done.md)

> **Never mark work done on a manually-modified build.** Do not call a feature complete ("works"/"proven") if the only verification ran on a build you hand-modified to make it pass — a paused GitOps auto-sync, a manual `kubectl apply` of branch manifests, an out-of-band cloud change, a mid-session policy patch. Those prove the *mechanism*, not the *delivered artifact*. Completion requires verifying behavior on a build with no manual changes: a clean bring-up from committed source (GitOps/CI/Terraform), after a teardown to the relevant phase where feasible. If a clean build cannot be run yet, say so and mark "pending clean-build verification" — never "done".
>
> *Grounded in: the sandbox-kubectl spoke proof ran inside a paused-auto-sync window with hand-applied branch manifests, and was repeatedly called "done".*

The spoke proof paused ArgoCD auto-sync and hand-applied the branch Composition, then was called "done on both clusters" several times despite the owner's explicit clean-build requirement. A manual apply proves the mechanism but not that a clean GitOps/Terraform bring-up reproduces it — the exact gap that hides integration bugs until the next real deploy. Cost of the rule: one honest label + one clean bring-up before merge. Cost of skipping: shipping "done" work that never ran the way it ships.

### Suggestion 2: A red gate is real — fix it or delete it, never re-kick or relegate to a schedule — `AGENTS-MD-e2e2a5161b`

- **Per-rule file**: [./2026-06-08-184/AGENTS-MD-e2e2a5161b-red-gate-is-real-no-nightly.md](./2026-06-08-184/AGENTS-MD-e2e2a5161b-red-gate-is-real-no-nightly.md)

> **A red gate is real — fix it or delete it; never re-kick or relegate to a schedule.** A gating check that is red is a real signal every time. Do not "re-kick until green", do not merge around it, do not narrate why it "doesn't really matter". If the code is wrong, fix the code; if the check is non-deterministic (flakes for reasons unrelated to the change — eventual consistency, ordering, timing), the check itself is the defect: make it deterministic (a bounded poll on the real condition that accepts every valid terminal state). There is no "nightly" and no "non-gating" lane to hide a check in — a behavioral check either gates fail-closed at its proper surface or it is fixed/deleted. Re-running is legitimate only for a genuinely external infra blip, and even then the flaky check gets filed and fixed, not normalized.
>
> *Grounded in: a known ASM-deletion flake was re-kicked 3× before being recognized as a deterministic-poll fix, and a "nightly real-AWS" exclusion lane was found shunting real behavioral tests off the gate.*

The chainsaw red was a one-shot `describe-secret` racing ASM's eventually-consistent deletion; the reflex was to re-dispatch three times and explain it away — how a team learns to ignore red. Plus a `CHAINSAW_INCLUDE_REALAWS`/nightly lane excluded real behavioral tests and substituted lints + a manual runbook. Cost of the rule: one deterministic rewrite or one deletion. Cost of skipping: every future session re-discovering that red is untrustworthy.

### Suggestion 3: Verify behavior coupled to the build under the real identity — `AGENTS-MD-b0257653bf`

- **Per-rule file**: [./2026-06-08-184/AGENTS-MD-b0257653bf-verify-behavior-coupled-real-identity.md](./2026-06-08-184/AGENTS-MD-b0257653bf-verify-behavior-coupled-real-identity.md)

> **Verify behavior coupled to the build, under the real identity.** A test must prove the thing *works*, not that a manifest *says* it does. Static `yq`/`grep` checks are the push/PR floor only — never the oracle. The center of verification is driving the real controller under its real IRSA identity and checking the real cloud resource, on by default and coupled to the build. Cluster/live work is `workflow_dispatch`-only; push/PR stays static. Never weaken a behavioral check down to a green lint.
>
> *Grounded in: driving the real Composition on a second live cluster surfaced a upjet provider bug and a missing IAM permission that render/yq lints could never have seen.*

Every static check passed; only the live run under the real crossplane identity revealed the upjet `SecurityGroupIngressRule` observe bug and the missing `ec2:AuthorizeSecurityGroupIngress`. Both would have shipped silently. This is ADR-0006; the cost is dispatch time, the alternative is serial production discovery of the unknown-missing-permission class.

### Suggestion 4: Check sequential doc numbers against the tree and open PRs before assigning — `AGENTS-MD-44ea6a9414`

- **Per-rule file**: [./2026-06-08-184/AGENTS-MD-44ea6a9414-check-doc-numbers-against-tree-and-prs.md](./2026-06-08-184/AGENTS-MD-44ea6a9414-check-doc-numbers-against-tree-and-prs.md)

> **Check sequential doc numbers against the tree and open PRs before assigning one.** Before assigning a sequential identifier that humans curate (an ADR number `docs/decisions/NNNN-*`, a migration number, a fixture index), list the existing ones (`ls`) AND check open/unmerged PRs for reserved numbers — sequential numbers collide across concurrent branches. Prefer content-hash IDs (as `retrospective/` already uses) for anything assigned off a branch. If you must use a sequential number, pick the next free one only after both checks.
>
> *Grounded in: an ADR was authored as 0006 (taken on the branch's base) and then 0007 (taken in an unmerged PR) before the real next free number was found.*

Two wrong ADR numbers, an owner correction, and a rename pass — pure tax on a doc unrelated to numbering. Cost of the rule: one `ls` + a PR glance (or just use the hash IDs the retro tooling mints). Cost of skipping: a collision discovered later, then a rename + reference-fix sweep.

### Suggestion 5: Reconcile with origin/main at session start before numbering or basing new work — `AGENTS-MD-8403820814`

- **Per-rule file**: [./2026-06-08-184/AGENTS-MD-8403820814-reconcile-origin-main-at-session-start.md](./2026-06-08-184/AGENTS-MD-8403820814-reconcile-origin-main-at-session-start.md)

> **Reconcile with `origin/main` at session start before numbering or basing new work.** The sandbox clones the repo once at container start, so a session can be behind `main` by the time you act. Run `git fetch origin main` and rebase/merge (or branch off the freshly-fetched `origin/main`) before doing anything order-sensitive — numbering, basing a new branch, or assuming a file's latest content. A stale base silently hides files and conventions that already exist on `main`.
>
> *Grounded in: the working branch was 4 commits behind main — missing two committed ADRs — which caused an ADR-number collision and a "where is this file" investigation.*

The branch was cut at container-start and never re-synced; `main` advanced 4 commits (the two ADRs that caused the collision). Time lost spelunking for "missing" files. Cost of the rule: one `git fetch` + reconcile at the top. Cost of skipping: order-sensitive decisions made against a stale snapshot.

### Suggestion 6: Regenerate generated goldens to a temp path, never redirect into the fixture — `AGENTS-MD-b78c3d8f3f`

- **Per-rule file**: [./2026-06-08-184/AGENTS-MD-b78c3d8f3f-regenerate-goldens-to-temp-not-fixture.md](./2026-06-08-184/AGENTS-MD-b78c3d8f3f-regenerate-goldens-to-temp-not-fixture.md)

> **Regenerate a generated golden to a temp path, then move it in — never `> the-fixture-file`.** A shell redirect (`cmd > expected.yaml`) truncates/creates the target *before* the command runs, so a tool that diffs against an existing golden will see an empty file, emit a (possibly truncated) diff, and you capture the diff instead of the golden. Generate to a temp file, sanity-check it (expected kinds/length), then `cp`/`mv` it into place; re-run the checker to confirm it matches.
>
> *Grounded in: regenerating a composition render golden with `> expected.yaml` captured a 200-line truncated diff instead of the 462-line render.*

`composition-render.sh ... > expected.yaml` created an empty file first, so bootstrap mode didn't trigger, it diffed against empty, truncated at 200 lines, and that diff became the "golden". An extra debugging cycle to spot. Cost of the rule: one temp file + a `mv`. Cost of skipping: a golden that passes against itself but encodes garbage.
