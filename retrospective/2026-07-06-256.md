## Part 1 — what happened

The session ran the parallel **documentation track** of a two-session split: a build/identity session owned the live AWS account, `ai/handoff.md`, and the heavy CI workflows; this session owned `docs/site/**`, the docs generator, and the docs CI gate. The hard boundary held throughout except for two owner-directed deviations (into `docs/open-issues.md` and the SHA-verifier gates), both explicitly authorized mid-session.

### Phase 1 — Wave 1: skeleton + publishing pipeline (PR #247)

Goal: an mkdocs+material diataxis skeleton with the stability-marker convention that keeps docs-before-implementation honest. The load-bearing piece is `docs/hooks/status_banner.py`: every page must declare `status: stable|contract|draft` front matter; a missing/invalid marker logs a `mkdocs.*` warning that `mkdocs build --strict` promotes to a failure. I verified the gate in both directions (injected `status: bogus` → exit 1, restored → green) before committing — the discipline is mechanical, not memorized. The Pages publish workflow could not go through git push (the credential lacks `workflow` scope), so it went via the jentic bridge (ext-github §8). Mid-PR, `test_root_file_allowlist.sh` correctly rejected a root `mkdocs.yml`; rather than touch the test (out of my boundary), I relocated the config to `docs/mkdocs.yml` with rebased paths — the lint working as designed, redirecting a convention.

### Phase 2 — Wave 2 exemplar + the permission storm (PR #249)

Goal: exactly one exemplar how-to (provision a platform secret) as the template all other pages follow, then stop for owner review. Authored from committed sources (XRD, Composition, ADR-0012, chainsaw scenarios), marked `stable` on that evidence, v2 vocabulary throughout (XR, never "claim"). The owner merged it — approving the template — but the salient event of this phase was operational: **every MCP call was prompting for permission**, and prompts that died during sandbox suspends read to me as transient tool errors, so I retried them, and each retry re-prompted — buzzing the owner's watch repeatedly. The owner's reaction was sharp and correct. I diagnosed the real cause (no `.claude/settings.json` permission allowlist existed) and committed one, first session-local then repo-wide, for the three standing MCP servers.

### Phase 3 — the full "now" wave (PR #254)

On owner direction ("get enough docs done that I can start scenarios ASAP"), I wrote the entire remaining "now" wave in one cross-linked PR: 7 how-tos, 5 reference pages, the first-application tutorial, the topology explanation — 14 pages, all `stable`, all authored from committed sources (AppProjects, ApplicationSets, the hello chart, the keycloak DB/secret consumers, ADR-0003/0010/0012). Strict link validation coupled the wave, which is why it shipped as one PR. `mkdocs build --strict` caught a bad heading anchor mid-work — the gate earning its keep.

### Phase 4 — the docs-blindness experiment (no PR; produced the review that drove #256)

The owner challenged the "now wave complete" claim: *could any wave-1 scenario actually be written to L1 from the docs alone?* I ran a six-agent docs-blind fan-out — each subagent given ONLY the published site URL, forbidden repo access, covering all 20 wave-1 scenarios. The agents converged independently on real defects, including two I could not see from inside the repo: a **cross-page access contradiction** (tutorial/health pages require kubectl the onboarding page says doesn't exist) and a **5-vs-6 resource enumeration mismatch** between two pages. Verdict: 12 writable / 6 partial / 2 not writable.

### Phase 5 — the L1 readiness package + the gate detour (PR #256)

Two owner rulings reshaped the fix: (1) bring-up is user-facing (the owner is a user), so the missing rebuild page is a real gap, not an audience-rule exclusion; (2) an operator hand-grant is a **defect to report**, not a procedure to document — my first draft papered the access gap with hand-off prose, which the owner rejected because it hides the gap from the blocked-on-docs metric. I registered five open issues, wrote the `l1-readiness-review.md` record, added two new pages (bring-up as `contract`, finished-platform inventory as `stable`), and fixed 11 pages. Then the rebase onto a moved `main` tripped both fail-closed SHA-verifier gates — the push-path filters fire on the ref-update diff, which over-fires on a rebase force-push. Owner approved fixing the gates over routing around them: I gave both verifiers a merge-base change-set decision with a `none` tier, pinned by unit tests, shipped in the same PR — proving itself green on its own head.

## Part 3 — remedy proposals (classified per `ai/LESSONS.md` §3)

Per the 2026-06-10 amendment, proposed remedies are classified rather than written as `AGENTS-MD` files: (a) mechanical check, (b) one-line AGENTS rule, (c) structural S-item for the owner, (d) observation.

### Proposal 1 — (b) Report a defect as a defect; never paper it with a workaround-as-procedure

> **Defects stay visible.** "When a documented step only works via an undocumented hand-fix (operator hand-grant, manual patch, out-of-band write), report it as a defect / blocked-on-documentation and register it — never dress the workaround up as a supported procedure. A workaround presented as a step hides the gap from the metric that is supposed to catch it."
>
> *Grounded in: the access-acquisition gap in PR #256, where the owner rejected my hand-off prose.*

**Justification.** I first documented the kubectl-access gap as an "operator → tenant hand-off" with numbered sub-steps — which reads as *this is how it works*. The owner's correction was exact: the whole point of the docs-blindness corpus is that its blocked-on-docs count measures real gaps; a workaround written as a procedure makes the count go blind to the very defect it exists to surface. The marginal cost of the rule is one sentence of framing per gap ("no documented way to do X exists — this is a registered defect"); the cost of omitting it is a metric that silently under-counts, which defeats the corpus's entire diagnostic value.

### Proposal 2 — (b) Register findings you discovered and understand; do not hand them to the owner to file

> **Own your findings.** "A finding you discovered and understand is yours to register in the repo's own mechanisms (`docs/open-issues.md`, a plan/handoff doc) — never end a task by telling the owner 'that's yours to file.' Fold it into a durable artifact and get it done."
>
> *Grounded in: the owner's rebuke after I labeled the XDatabase / cross-tenant-secret / CRB findings as 'yours to file' in Phase 4.*

**Justification.** After the docs-blindness experiment surfaced three product defects, I closed by assigning them to the owner as issues to file. The owner's response — "do not abdicate responsibility to me for something you found. If you understand it, you can help fix it" — is a general principle: the agent that has the context to state a finding precisely is the cheapest place to register it. The repo already mandates that undiagnosed failures get an open-issue entry (AGENTS.md "no silent skips"); this extends the same discipline to *diagnosed* findings. Marginal cost: writing the OI entry I already understand. Cost of omitting: the owner does clerical work I was better positioned to do, and findings risk evaporating in the hand-off.

### Proposal 3 — (a) [ADOPTED this session] Change-set-aware applicability for path-filtered CI gates

Mechanical fix shipped in PR #256: `required-profile-for-changes.sh` gained a `none` tier, and both SHA-verifier gates now decide applicability from the merge-base change set rather than the push-path trigger. A rebase force-push over a moved `main` carries that main's recent history through the ref-update diff, so path filters over-fire. Pinned by `test_live_evidence_gate.sh` (all three tiers, plus the machinery-circularity case). See ADR-c87dd95a8c. No further action; recorded here as the durable lesson behind the fix.

### Proposal 4 — (a) [ADOPTED this session] Commit an MCP permission allowlist for standing servers

Mechanical fix shipped in PR #249: `.claude/settings.json` allowlists the three MCP servers a session uses as standing infrastructure (claude-code-remote, jentic, github). Absent it, every MCP call falls through to an interactive prompt → push notification. No further action; recorded as the lesson.

### Proposal 5 — (d) Recognize the dead-prompt retry loop

> *Observation.* A permission prompt (or scheduling call) that dies during a sandbox suspend surfaces as a "stream closed"/tool error that pattern-matches a transient failure. Blindly retrying re-issues the prompt — another notification. When a permission-gated call fails with a connection/stream error, suspect a dead prompt and fix the permission (allowlist) rather than retrying the call. No mechanical remedy proposed beyond Proposal 4; flagged so a future session recognizes the signature.

### Proposal 6 — (b) Re-Read files after a branch reset or rebase

> **Stale-read guard.** "After `git checkout -B <branch> origin/main`, a rebase, or any operation that moves HEAD, re-Read a file before editing it — in-session reads taken before the move are stale, and the editor will (correctly) refuse with 'File has not been read yet.'"
>
> *Grounded in: repeated Edit failures across PR #254 and #256 after resetting the branch from merged main.*

**Justification.** Each PR merged and I reset the branch from `main` to start the next; several Edit calls then failed because the harness's file-state tracking had been invalidated by the reset. It cost a re-Read each time — cheap individually, but a recurring stutter. The rule is one Read before the first Edit on any file touched after a HEAD move. Low signal but real; include only if the AGENTS budget has room, else leave as an observation.
