### Phase 3 — phase-5 identity, built during the build's waits

All identity work overlapped provisioning waits. The documentation plan's

three `status: contract` pages that double as the spec. Then the

### Phase 4 — the evidence pass, and live-verify's red that was real

All six oracles ran from the sandbox as recorded checks (RUN_ID
`build5-2347`), all PASS, including the material chain's first
oracle-recorded evidence. Then live-verify.yml — dispatched on main for
the OI close — went RED, and the red was the most valuable event of the
session: the suite's first run against a fully-converged substrate under

and, after granting `ec2:DescribeInstances`, the relay check got far
enough to hit the missing `ssm:StartSession` and reported "SG ingress /

got a durable gate: `test_verifier_policy_covers_check_reads.sh`
extracts every `aws` call from the after tier and asserts the policy
grants it — which also caught, pre-emptively, that the brand-new
phase-5 checks needed `eks:*IdentityProviderConfig*` reads.

## §3.4 — operational mishaps (recorded verbatim; the mishap IS the lesson)

1. **A fabricated run ID.** While drafting the OI-2026-06-12-1 close
   text before the branch live-verify run had completed, I typed
   "run 28759921550" — a plausible-looking, entirely invented number.
   Caught within one tool call and replaced with the explicit token
   `RUNID-LIVE-VERIFY-BRANCH`, resolved to the real `28760138628` in a
   later commit. In an evidence ledger whose entire purpose is
   click-to-audit run IDs, this is the worst possible silent failure;
   it motivated remedies 5 and 6.
2. **The staged-docs sweep.** Evidence docs were staged early ("ready
   for later") ; the subsequent relay-fix commit — made with explicit
   paths on the command line — ALSO swept the staged files in, pushing
   placeholder-bearing docs one commit early. Benign here (the
   placeholder was explicit and resolved next commit) but the mechanism
   is a footgun: `git commit <paths>` commits those paths PLUS whatever
   was already staged. Rule of thumb adopted mid-session: stage only at
   the moment of committing.
3. **Hang theory ahead of clock evidence.** I mis-estimated a
   live-verify run as 25 minutes elapsed (actual: 9) and spent real
   effort on a mutex-deadlock hypothesis and an endpoint probe before an
   API response's `Time:` header corrected the clock. Elapsed time must
   come from tool-returned timestamps (dispatch `created_at` vs. the
   probe's response time), never from felt duration across a
   context-dense session.
4. **The redirect race.** `scripts/composition-render.sh ... >
   expected.yaml` created the empty golden BEFORE the script ran, so the
   script diffed against the empty file it was meant to bootstrap.
   Standard shell behavior, momentarily confusing; re-run via a temp
   file. (Not proposing a rule; it's a one-keystroke class with an
   obvious tell.)

## §3.7 — runtime discoveries worth remembering

- **Keycloak 24.0.5 `--import-realm`**: `${VAR}` env substitution is
  real, happens before import-time validation, and unset placeholders
  pass through verbatim (all three facts probed empirically in docker —
  the web record is contradictory across versions). Startup import
  strategy is IGNORE_EXISTING: a live realm NEVER re-imports, so realm
  changes converge only at the next fresh-database build.
- **provider-upjet-aws `IdentityProviderConfig`**: the external-name IS
  the EKS `identity_provider_config_name` (injected via
  `SetIdentifierArgumentFn`; TF id is `cluster:name`), and the v2 CRD's
  `oidc` block is a single object, not an array.
- **The scoped-role blind spot**: every live check is developed under
  admin sandbox creds; nothing exercised the verifier role until
  live-verify ran on a converged substrate. Now mechanically closed for
  the read-verb class (remedy 1), but the general shape — "the check
  passes where it was written, lies where it runs" — is worth carrying.
- **Assume-the-role to reproduce**: `aws sts assume-role` into the
  verifier role from the sandbox (with the required session tag)
  reproduces CI's exact permission errors in seconds — far tighter than
  dispatch-and-read-logs iteration.
