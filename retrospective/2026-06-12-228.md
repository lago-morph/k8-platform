### Phase 2 — the keycloak DB path (OI-2026-06-07-5), premise-first

The recorded Decision 3 mechanism flagged its own premise as unverified, so the helm-render fixture came **first**: bitnami/keycloak 21.4.4 routes `externalDatabase.host/port` through the `keycloak-env-vars` ConfigMap consumed via `envFrom`, and `extraEnvVarsSecret` renders as a *later* envFrom source — Kubernetes resolves duplicate envFrom keys last-source-wins, so the override is structurally sound (12/12 assertions). Only then was the chain wired: hub PushSecret → ASM `k8-platform/keycloak-db` → spoke ExternalSecret remapping to `username/password/KEYCLOAK_DATABASE_HOST/PORT`, plus the spoke ESO baseline the chain rides on (eso ApplicationSet, ClusterSecretStore, XSpokeAccess eso-role/policy pair, a sixth contract key `eso-role-arn` with the ADR-0010 amendment). Two live verifications de-risked the merge: the connection-secret key names against the real provider output (`host` is the bare hostname; `endpoint` is host:port and would have been wrong), and the registration-secret contract. Repo archaeology surfaced that the keycloak XPlatformSecret XRs and realm ConfigMap had *never been synced by anything* — the realm CM moved to the spoke directory source (re-waved 36 → −1 to avoid an ArgoCD wave-health deadlock), and keycloak-admin got an interim spoke-local generator.

### Phase 3 — merge #226, then the convergence loop caught four real defects

#226 merged after its chainsaw went green; GitOps + one management apply converged the live substrate, and the loop worked exactly as designed — each failure produced a code fix, not a hand-fix: (1) **kyverno** admission controller OOM-crashlooping with all report-cleanup CronJobs ImagePullBackOff on the unpullable `bitnami/kubectl:1.28.5`; its fail-closed webhook blocked hub applies *including its own helm upgrade hook* — the first fix apply died in that bootstrap deadlock, but helm applies manifests before post-upgrade hooks, so the fixed Deployment was already live and the re-run recorded the release. (2) **`ec2:CreateSecurityGroup`** denied under the narrowed policy: it authorizes against the security-group *and* the vpc resource, and the vpc type carries no `ec2:Vpc` condition key — fixed with a resource-pinned Sid. (3) **`rds:ModifyDBInstance`** denied on the `subgrp:` resource — same multi-resource-auth class, second instance in one evening. (4) the **keycloak chart image** itself unpullable (same Bitnami pullback class). Each IAM fix was validated by a branch `apply-and-verify` run before riding the PR. The RDS base-VPC move then hit a hard AWS wall: the instance sat in us-east-1d, the base VPC spans only 1a/1b, and ModifyDBInstance cannot change AZ — the planned git-driven delete/recreate became moot when the owner announced account rotation.

### Phase 4 — the material chain: built, fought, reverted with a diagnosis

Task 3's blocker was structural: `derive_expect_full` derives expected kinds from committed Compositions, so live-verify can never go green without a *valued* XPlatformSecret — and the abstraction provisions empty, uid-named shells. The redesign (deterministic `k8-platform/<ns>/<name>` naming + Password generator → generate-once ES → value writer) went through three real designs under chainsaw fire: an ARN-gated PushSecret (deadlocked on ESO's `managed-by=external-secrets` ownership check, verified against the v0.9.13 provider source), a pre-tagged container (papering over an ownership lie), and finally the crossplane-native **SecretVersion** writer (no gate, no ownership semantics — the ADR draft in the sibling dir). Four consecutive chainsaw runs died at the 30-minute job cap; the cap was raised to 45 via the jentic workflow PUT, the suspected cross-run name-collision got a pre-run sweep — and the decisive full-bounds run then failed *with the long-proven composition too*, on a clean ASM ("none found"), proving the redness environmental and content-independent. The honest move was a surgical revert of the three chain commits, shipping #227 as seven independently-validated fixes, with the full design + exclusion trail + next step (fix the catch blocks' namespaced-MR blindness) quarantined in OI-2026-06-12-1.

### R1 — (a) mechanical: chainsaw catch blocks must read v2 MRs namespaced — **CLOSED (implemented as a superset by the #230–#237 session; see status audit above)**

The single most expensive defect of the session was diagnostic, not functional: the catch blocks run `kubectl describe "$kind.$api" "$mrname"` with no `-n`, but every `.m.` provider MR is **namespaced** — so across four 30-minute chainsaw cycles the failing asm-secret MR's actual condition was never once visible, and each iteration was a guess. Fix (already specified in OI-2026-06-12-1): switch the catch loops to namespaced describes (`-A` enumeration), and add a unit lint asserting no chainsaw catch script addresses a `.m.`-group kind without `-n`/`-A`. Lands with the OI-2026-06-12-1 rework PR. Cost of absence: ~2.5 hours of blind iteration; cost of adoption: one script edit + one lint.

### R2 — (b) one-line AGENTS.md judgment rule: bisect the environment before iterating content — **ADOPTED (PR #238, L32)**

When the chainsaw gate failed identically across three *different* contents (chain, chain+tag, chain-with-SecretVersion), the productive move — re-running effectively-last-green content — happened only at the fourth iteration, via the revert. Proposed line: *"When a gate fails identically across content changes, stop changing content: re-run the last-green SHA (or equivalent) first to split content from environment."* On 2026-06-12 that split would have saved two 30-minute cycles and redirected effort to the diagnostic gap a cycle earlier. Budget cost: one line.

### R3 — (b) one-line AGENTS.md judgment rule: batch commits against SHA-exact gates — **ADOPTED (PR #238, L33)**

Six chainsaw dispatches were superseded by my own follow-up pushes (the verify gate matches exact HEADs and `cancel-in-progress: true` kills in-flight runs on the same ref). The existing "finalize commits before dispatching" line covers the working tree but not the *next* commit. Proposed sharpening of that existing line rather than a new one: *"…and do not push to a gated branch while its dispatch is in flight — batch the follow-ups."* Cost of absence this session: ~1.5 hours of gate latency.

### R4 — (a) mechanical: environment-fact additions to `ai/environment.md` — **ADOPTED (PR #238)**

Verified facts that will recur, to land as §6/§8 bullets in the next docs PR: (1) GitHub resolves a `workflow_dispatch` ref to `head_sha` at *run creation*, not job start — dispatch-after-push or the run tests the wrong SHA; (2) `chainsaw.yml` has `cancel-in-progress: true` per ref — any same-ref push or dispatch cancels the in-flight run; (3) helm applies manifests *before* post-upgrade hooks — a hook-failed release can still have landed its manifests (the kyverno bootstrap-deadlock escape); (4) kind cannot run in this sandbox (`docker exec --privileged` exits 128) — the chainsaw inner loop is CI-only; (5) AWS multi-resource authorization: one API call can authorize against several resource types with different condition-key support (`CreateSecurityGroup` → security-group+vpc; `ModifyDBInstance`+subnet-group → db+subgrp) — check the SAR resource table before conditioning any new action.

### R5 — (d) observation: the premise-first fixture discipline paid for itself twice

Decision 3's "prove last-wins before wiring" produced a 12/12 fixture that took ~20 minutes and made the riskiest part of the DB path boring; the live key-name verification (host vs endpoint) caught a wrong-shape value pre-merge. Conversely, the material chain shipped with *two* unverified premises (ESO ownership semantics; gating timing) and burned hours. No new rule needed — ADR-0006/the existing discipline already says this; recorded as reinforcing evidence.

### R6 — (d) observation: quarantine-with-diagnosis is the right failure mode for a blocked feature

Reverting the chain off #227 (preserving seven validated fixes) with the full design + exclusion trail in OI-2026-06-12-1 converted a stuck PR into a mergeable one plus a precisely-scoped successor task. Pattern worth repeating; no rule text proposed.
