## Part 1 — what happened

### Phase 1 — orient + resolve the two phase-3 entry decisions

Goal: implement phase 3 (platform-services cluster). The user supplied the
two answers that had blocked it: the D1 subnet question ("use terraform
output") and "GitHub CICD credentials are correct." Reading PR #138's
retrospective confirmed D1: a tag-based `subnetIdSelector` is infeasible
(Crossplane selectors match k8s labels on Crossplane-managed resources, not
AWS tags), so subnets come from the base Terraform output. The phase-0 build
the user referenced (run `26985472847`, base apply-and-verify) had completed
green, so the foundation was live at session start.

The user then redirected TLS twice — first replacing the original
cert-manager + Let's Encrypt design with a **real ACM certificate via a

provisioning every cluster** (folded into the cluster Composition), not a
one-off. A short Q&A established where the cluster XRD/Composition lives
(`crossplane/`, deployed to the management cluster; instances under
`clusters/<name>/`), which confirmed the cert belongs inside the shared
cluster Composition.

### Phase 2 — build + locally validate the core (Waves 1–3, 5a)

The riskiest, user-flagged piece (the ACM cert) was de-risked first by
getting `crossplane render` working locally. That required real sandbox

The cluster Composition then provisioned (in render) all 11 MRs including

`Record`, and `CertificateValidation`. Terraform plumbing (eks/iam/acm/
route53 providers + function-environment-configs + IRSA ACM/Route53 + the
EnvironmentConfig from base outputs) landed in `terraform/management`.
Let's Encrypt/cert-manager references were removed from active docs; a
future-enhancements note and ADR 0003 captured the decision. CI: unit-tests
+ terraform-validate green; a stale contract test and the platform-cluster
chainsaw scenario were realigned to the new `dns` schema; live chainsaw
`xrd-establishes` passed (run 26993676391).

### Suggestion 1: Distinguish provisioning from verification in a GitOps repo — `AGENTS-MD-429a56a4b8`

- **Per-rule file**: [./2026-06-05-140/AGENTS-MD-429a56a4b8-distinguish-provisioning-from-verification.md](./2026-06-05-140/AGENTS-MD-429a56a4b8-distinguish-provisioning-from-verification.md)

**Proposed agent instruction:**

> **Distinguish provisioning from verification in a GitOps repo.** In a GitOps repository, do not tell the user they must "provision" or "apply" something manually when ArgoCD/Crossplane/CI converge it from git. Before describing any step as a manual user action, ask whether GitOps or a CI workflow already performs it; reserve "manual" for the genuine gaps (a deliberately-disabled auto-sync, a Terraform bootstrap the agent itself dispatches). When you cannot complete a step, name the real blocker — usually verification access, not provisioning.
>
> *Grounded in: 2026-06-05 phase-3 — agent framed the spoke as "you must provision"; user replied "aren't we using gitops here?"*

**Justification:**

The agent twice told the user to "provision" the platform cluster, when in
fact ArgoCD + Crossplane provision it from git and the agent's only real
limitation was that the sandbox can't *verify* convergence (no cluster
creds). The mis-framing cost the user two rounds of pushback and eroded
trust ("why do I have to provision anything?"). The marginal cost of the
rule is one question at framing time — "does GitOps/CI already do this?" —
which would have produced an accurate "I can author + drive this; I just
can't watch it converge from here" instead of an incorrect hand-off.

### Suggestion 2: Probe for cloud and cluster access before declaring the cluster unreachable — `AGENTS-MD-e29829c1b3`

- **Per-rule file**: [./2026-06-05-140/AGENTS-MD-e29829c1b3-probe-cluster-access-before-declaring-unreachable.md](./2026-06-05-140/AGENTS-MD-e29829c1b3-probe-cluster-access-before-declaring-unreachable.md)

**Proposed agent instruction:**

> **Probe for cloud and cluster access before declaring the cluster unreachable.** Before claiming you cannot reach the cluster/ArgoCD/cloud, actually probe: AWS_* env vars, ~/.aws, IMDS (169.254.169.254), $KUBECONFIG and ~/.kube, a test call to a cloud API endpoint, and any credential-brokering MCP. Report the specific failure (no creds vs blocked egress vs missing tool). If the install path for driving the service is to expose its credentials as a Terraform output, prefer that over asserting impossibility.
>
> *Grounded in: 2026-06-05 phase-3 — agent repeated a stale "can't kubectl" claim; user said "you have access or can generate ArgoCD credentials."*

**Justification:**

The agent carried forward a prior session's "sandbox can't reach the
cluster" note as if it were a standing fact, instead of probing. When it
finally probed (per §6.12), it found the precise truth — egress works,
credentials don't exist — which is materially different from "can't reach
it" and points at the real fix (create+output ArgoCD creds, drive via CI).
The probe is five cheap commands; the cost of skipping it was an inaccurate
capability claim the user had to challenge.

### Suggestion 3: Bypass a blocked image registry by retagging from an alternate registry — `AGENTS-MD-b56f4a5eff`

- **Per-rule file**: [./2026-06-05-140/AGENTS-MD-b56f4a5eff-registry-retag-workaround.md](./2026-06-05-140/AGENTS-MD-b56f4a5eff-registry-retag-workaround.md)

**Proposed agent instruction:**

> **Bypass a blocked image registry by retagging from an alternate registry.** When a local tool fails to pull a required image because one registry is blocked or returns 5xx (e.g. ghcr.io 503), check whether the same image is published on an alternate registry (e.g. docker.io), pull it there, and `docker tag` it to the blocked reference so the local daemon finds it cached. Verify per AGENTS 6.12 before declaring the tool unusable.
>
> *Grounded in: 2026-06-05 phase-3 — `crossplane render` failed pulling `xpkg.crossplane.io/crossplane/crossplane:stable` (ghcr 503); pulled `crossplane/crossplane:stable` from docker.io and retagged.*

**Justification:**

`crossplane render` — the author-time SPEC-S9 gate — was dead in the sandbox
because the core image's registry (ghcr.io) returned a hard 503, while the
function images (xpkg.upbound.io) pulled fine. Without the retag workaround
the entire local validation loop is unavailable and every Composition change
must round-trip through CI. The workaround is two commands and unblocked the
whole session's local iteration; the asymmetry is large.

### Suggestion 4: function-patch-and-transform — combine cross-source values via top-level environment.patches — `AGENTS-MD-89f9b55781`

- **Per-rule file**: [./2026-06-05-140/AGENTS-MD-89f9b55781-pt-env-combine-top-level-environment-patches.md](./2026-06-05-140/AGENTS-MD-89f9b55781-pt-env-combine-top-level-environment-patches.md)

**Proposed agent instruction:**

> **function-patch-and-transform: combine cross-source values via top-level environment.patches.** To build a value that combines an XR field with an EnvironmentConfig field (e.g. a wildcard domain from spec.dns.subdomain + env.domain), stage the XR field into the environment with a TOP-LEVEL `environment.patches` entry (which runs before resource patches) and then CombineFromEnvironment on the resource. A per-resource ToEnvironmentFieldPath write is NOT visible to a CombineFromEnvironment in the same render/reconcile pass; the top-level environment patch is.
>
> *Grounded in: 2026-06-05 phase-3 — the cert domainName rendered empty until the subdomain→env write moved from a per-resource patch to a top-level environment patch.*

**Justification:**

Two render iterations were burned discovering that P&T's combine reads the
environment as it stood at the start of the pass, so a same-resource
ToEnvironment write produces nothing. The fix (top-level `environment.patches`,
which apply first) is non-obvious and not well documented. Recording it saves
the next author the same two-iteration discovery on any cross-source
combination (cert domains, ARNs, names) — a recurring Composition need.
