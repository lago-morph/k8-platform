The user opened with a high-level intent: "the agent in a prior session

### Phase 2 — evidence-first survey

Before changing code, the agent surveyed `.github/workflows/`, the
helper scripts, and every doc referencing `trigger-action`,

### Phase 3 — coherence check before code

The user asked a sharp question at this point: *"Will that plan still
be coherent after we are done, assuming the agent can access the full
GitHub API?"*

is parameterized by `(phase, action)` via `workflow_dispatch`, and the

that did the agent get approval to write code.

### Phase 4 — cleanup, then fence

updated the unit tests (`compute-gates.sh` lost its `event` argument),

do not resurrect" block in the ext-github spec and a new
"Authoritative specs" section in `CLAUDE.md` naming the spec as

### Phase 5 — prompt design for the next session

## Part 4 — proposed ADRs

Architectural decisions made or reaffirmed in this session that the
user may want to record formally. **Titles only — no specs.** Use the
`adr` skill to author any that earn the slot.

- **CI auto-triggers reserved for non-mutating checks only.** All
  Terraform, Kubernetes, and AWS-touching workflows must be
  `workflow_dispatch`-only; auto-triggers (`push`, `pull_request`,
  branch-name patterns) are permitted only for read-only validation
  (lint, fmt, validate, schema-check).
- **Agent-sandbox workarounds must be tagged and removed when the
  limit lifts.** Code that exists to bypass an agent-environment
  constraint (no `workflow_dispatch` primitive, no direct API access,
  etc.) is technical debt and must be marked as such in its header
  comment so a future session can identify and remove it when the
  constraint goes away.
- **`ai/specs/*.md` are authoritative within their scope.** When work
  is scoped to a design spec, that spec overrides historical files,
  prior commits, and surrounding code patterns. Conflicts resolve in
  favor of the spec; ambiguity is escalated to the user, not
  synthesized away.
