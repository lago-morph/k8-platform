## Part 3 — agents-file suggestions

### Suggestion 1: Verify a Crossplane package tag is published + version-compatible before pinning — `AGENTS-MD-34dd0a2e6c`
- **Per-rule file**: [./2026-06-07-162/AGENTS-MD-34dd0a2e6c-verify-package-tag-published.md](./2026-06-07-162/AGENTS-MD-34dd0a2e6c-verify-package-tag-published.md)

**Proposed agent instruction:**
> **Verify a Crossplane package tag is published and Crossplane-version compatible before pinning it.** "Before pinning any Crossplane provider/function package tag in terraform, confirm the exact tag exists in `xpkg.upbound.io` (marketplace or a registry HEAD) and supports the cluster's Crossplane major version. `crossplane render` and kubeconform do NOT validate the package reference, so a wrong or non-existent tag passes every local check and only fails at live install with `MANIFEST_UNKNOWN` 404."
>
> *Grounded in: auto-011 — provider-kubernetes:v0.16.0 was never published to xpkg and predated Crossplane v2; the management apply failed only at install.*

**Justification:** A subagent guessed `provider-kubernetes:v0.16.0`; it passed render + kubeconform + terraform plan and only blew up after a full management apply reached its last step (`MANIFEST_UNKNOWN`), costing a ~20-min apply cycle. The registry actually publishes v0.18.0/v1.0.0–v1.2.1, with v1.x being the Crossplane-v2 line. One marketplace/registry check (or a `crane`/HEAD) before pinning is seconds; the alternative is a late-stage apply failure on the live cluster.

### Suggestion 2: terraform_data applying an inline manifest needs a body sentinel in triggers_replace — `AGENTS-MD-e113cd4693`
- **Per-rule file**: [./2026-06-07-162/AGENTS-MD-e113cd4693-terraform-data-manifest-sentinel.md](./2026-06-07-162/AGENTS-MD-e113cd4693-terraform-data-manifest-sentinel.md)

**Proposed agent instruction:**
> **A `terraform_data` that applies an inline manifest must carry a manifest-body sentinel in `triggers_replace`.** "When a `terraform_data` resource `kubectl apply`s an embedded manifest via local-exec, a body-only edit (e.g. adding `runtimeConfigRef`) does not change the version-variable triggers, so `terraform apply` silently no-ops the change. Add (and bump) an explicit sentinel string — or `sha256()` of the manifest — to `triggers_replace` whenever the manifest body changes."
>
> *Grounded in: auto-011 — adding runtimeConfigRef to the child-provider manifests required a `runtimeconfigref-irsa-2026-06-06` sentinel; helm.tf already documents this trap 3×.*

**Justification:** The codebase has hit this trap repeatedly (helm.tf carries three comments about manifest-body edits no-op'ing the apply). When adding `runtimeConfigRef` to the child providers, omitting the sentinel would have produced "Apply complete, 0 changed" while the live providers stayed broken — a silent failure that looks like success. The sentinel is one array element; the cost of forgetting it is a deceptive green apply and continued breakage.

### Suggestion 3: Validate unmerged Terraform against the live account before merging — `AGENTS-MD-db87a3ee76`
- **Per-rule file**: [./2026-06-07-162/AGENTS-MD-db87a3ee76-validate-unmerged-terraform-live.md](./2026-06-07-162/AGENTS-MD-db87a3ee76-validate-unmerged-terraform-live.md)

**Proposed agent instruction:**
> **Validate unmerged Terraform against the live account before merging.** "For terraform that can't be validated locally (no terraform binary in the sandbox), dispatch `terraform-test` `plan` on the feature-branch ref first to validate it without mutating, then `apply-and-verify`, then merge once the live apply is green. Never merge terraform to `main` that hasn't been proven against the live account — `main` should never be ahead of a successful apply."
>
> *Grounded in: auto-011 — the management plan on the branch ref caught nothing wrong, the apply surfaced the provider-kubernetes 404; #162 was merged only after a green apply.*

**Justification:** The sandbox has no terraform binary, so the only validation is CI against the live account. Running `plan` on the branch ref first confirmed the subagent's unvalidated `.tf` (envconfig + provider-kubernetes) parsed and planned cleanly (5 add / 4 replace) before any mutation; `apply-and-verify` then caught the bad package tag. Merging first would have put broken terraform on `main` and left `main` describing infra that never applied. The plan-then-apply-then-merge order keeps `main` honest at the cost of two CI dispatches.
