# Documentation plan — user-facing docs for k8s-platform (diataxis)

**What this is:** the plan for documentation as a first-class k8s-platform
deliverable. Initial requirement (owner-set, 2026-07-05): the docs must be
sufficient for the scenario corpus to be authored **without implementation
visibility**. Docs source lives in THIS repository (PR-coupled to the code,
like tests); it publishes to a GitHub Pages site; the published site is the
only thing scenario sessions may read. Derived from the seed scenario
catalog (`scenario-brainstorm.md`).

---

## Shape

- **Source:** `docs/site/` in this repo. Plain markdown, diataxis top-level
  split: `tutorials/`, `how-to/`, `reference/`, `explanation/`.
- **Generator:** mkdocs + material theme — the boring default for diataxis
  k8s documentation; pinned versions in the repo's usual way.
- **Publishing:** GitHub Pages via an Actions workflow on merge to `main`.
  (Note for the implementing session: the git push credential refuses
  `.github/workflows/**` — route the workflow file through the established
  jentic bridge, as previous workflow edits were.)
- **Audience rule:** every page describes **public surfaces only** — what a
  tenant, owner-as-operator, or engineer can see and do. If explaining
  something requires internals, it belongs in `explanation/` at the concept
  level or in the blog series, not in how-to/reference.

## Stability markers (docs-before-implementation, honestly)

Much of the documentation can and should be written before the features
finish — user-facing docs written first act as the **contract** the
implementation must meet (the same spec-first logic the platform already
uses for tests). To keep that honest, every page carries a status header:

| Marker | Meaning | Scenario corpus may |
|---|---|---|
| `stable` | Describes shipped, clean-build-verified behavior | Mature scenarios to L2+ against it |
| `contract` | Describes agreed-but-not-yet-shipped behavior (the implementation target) | Write L1 scenarios; L2+ blocks until it flips to `stable` |
| `draft` | Under discussion; may change without notice | Read, but not build on |

A page flips `contract → stable` only with clean-build evidence — the same
"done" bar as everything else in this repo.

## Content waves (mapped to the scenario catalog)

### Now (unblocks describing + spec'ing wave-1 scenarios)

**How-to (the workhorse quadrant — one task each):**
- Deploy an application via GitOps (scenario 4)
- Expose an application with a public hostname + TLS (5)
- Claim a database and connect to it (6)
- Claim a platform secret and consume it — including cross-cluster
  consumption via the deterministic secret naming (7)
- Update and roll back an application (9, 13)
- Check application health and find its URL (8)
- Onboard a tenant (3) — **documented as-is**: if today's honest answer
  involves owner hand-work, write that down; the scenario corpus will file
  it as the product gap it is. Documenting an ugly truth beats omitting it.
- Add a platform component / upgrade a component (11, 12)

**Reference (what oracles assert against):**
- XPlatformSecret spec (fields, defaults, the `k8-platform/<ns>/<name>`
  naming contract, the generated-material payload shape)
- XDatabase spec (fields, connection-secret keys)
- Tenant boundaries: what the project whitelists allow and deny (16–18)
- Platform hostnames and DNS/TLS conventions
- The health/status surfaces a tenant may read

**Tutorial (exactly one to start):**
- "Your first application on the platform" — the golden path stitched from
  the deploy + expose how-tos (feeds scenarios 4, 5, 23's pattern)

**Explanation (thin by design — the blog series carries depth):**
- One page: platform topology (hub/spoke, GitOps flow) at concept level

### With phase-5 identity (write as `contract` NOW, flip on evidence)

- How-to: get kubectl access via your directory group (21, 23)
- How-to: log into platform UIs with SSO (24)
- Reference: identity mapping (claims, the role prefix, group → access
  matrix; revocation bound) (22, 25)
- These pages double as the phase-5 spec — writing them first is
  deliberate: the implementation lands against them.

### With the storage fix

- How-to: view your application's logs and metrics (27)
- Reference: what observability signals tenants get (28, 29)

### With fan-out (phase 6)

- How-to: request/receive placement on a specific cluster (30, 31)
- Explanation: fleet model (32, 33)

## The sufficiency loop (how docs quality is measured)

The scenario corpus's **blocked-on-docs count** is the metric. After the
"now" wave publishes: every wave-1 scenario should be writable to L1 from
the site alone; each one that isn't files a docs bug naming the missing
page/fact. No other docs-quality metric is needed initially — this one is
generated by real use, which is the point of the whole design.

## Explicitly deferred (new requirements later, per owner scoping)

- PR-coupling enforcement (a lint requiring docs updates on public-surface
  changes) — desirable, but audit-before-enforce applies; revisit once the
  first documentation pass exists.
- A separate `k8s-platform-documentation` repository — named extraction
  path if publish cadence or repo visibility ever diverge; not now.
- Versioned docs (per platform release) — meaningless until the platform
  has releases.

## Execution notes for the implementing session

Small, self-contained waves; each is a normal docs PR (light gates only).
Sequence: (1) skeleton + publishing pipeline + landing page; (2) the "now"
how-tos + reference (the bulk — write from the public surfaces, verified
against a live build when available); (3) the `contract` pages for
phase-5, reviewed by the owner before the identity implementation starts.
The scenario corpus should be pointed at the site only after wave 2 of this
plan publishes, so its first blocked-on-docs pass measures a real attempt.
