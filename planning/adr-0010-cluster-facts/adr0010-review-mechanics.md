# ADR-0010 adversarial review — ArgoCD / ApplicationSet mechanics & transition semantics

Scope: mechanics only. Every claim below verified against the tree.

---

## BLOCKER

### B1. kubeconform will NOT actually validate the ApplicationSets — the schema is never fetched, so they go statusSkipped (a no-op NOTICE), not validated. The ADR's central static-verification promise is hollow.
- ADR claim: "`kubeconform-schemas/argoproj.io/` gains `applicationset_v1alpha1.json`" (line 107) and "Static (PR-1): kubeconform with the ApplicationSet schema" (line 115).
- Evidence: `scripts/fetch-crds-for-kubeconform.sh:136-137` fetches ONLY `application-crd.yaml` and `appproject-crd.yaml` from argo-cd `v2.13.1`. There is NO `applicationset-crd.yaml` URL. `kubeconform-schemas/argoproj.io/` (ls) contains only `application_v1alpha1.json` and `appproject_v1alpha1.json`.
- Consequence: `test_kubeconform_manifests.sh` runs with `--ignore-missing-schemas` (line 73) and treats a missing schema as `statusSkipped` → `_emit_notice` + continue (lines 348-351), NEVER a fail. So committing ApplicationSets with no schema produces a passing test that silently validated nothing. The ADR must add the `applicationset-crd.yaml` fetch URL to `scripts/fetch-crds-for-kubeconform.sh` AND commit the generated `applicationset_v1alpha1.json`, or the "kubeconform with the ApplicationSet schema" verification line is false.
- Fix: add `.../argoproj/argo-cd/<pinned>/manifests/crds/applicationset-crd.yaml` to `CRD_URLS`, regenerate the store, commit it; otherwise drop the kubeconform claim.

### B2. Bootstrap prune of the 9 plain Applications cascades-deletes the live spoke workloads mid-transition — the generated same-named Applications do NOT adopt the old apps' resources; they re-sync from scratch. The "selfHeal fight disappears, bootstrap never paused" framing hides a destructive transition.
- ADR claim: "when the 9 Application files are deleted and replaced by ApplicationSet files ... Generated Application names preserve today's names" implying seamless takeover (lines 54-60); "Bootstrap is never paused" (line 99).
- Evidence: the bootstrap App has `syncPolicy.automated.prune: true` (`argocd/bootstrap.yaml:47`). The 9 spoke Applications have NO `finalizers` (grep for `finalizers` under `argocd/` returns ONLY `bootstrap.yaml`). When the files are removed from git, bootstrap prunes the Application objects. Without `resources-finalizer.argocd.argoproj.io` on those Applications, Argo's default is non-cascading delete of the Application — but the new same-named Applications generated by the AppSet are DISTINCT objects (owned by the AppSet via ownerRef) and will perform a fresh sync. On `prune: true` spoke apps (every spoke app has it, e.g. `hello.yaml:30-32`) there is a real window where ingress-nginx/keycloak/hello are deleted-then-recreated. This is a genuine outage window the ADR does not acknowledge; "structurally disappears / never paused" is incorrect for the transition itself.
- Fix: document the cutover as non-atomic (either add the cascade finalizer deliberately + accept recreation, or do a same-PR swap and accept a sync blip), and state the blast radius. Do not claim a seamless takeover.

### B3. The hub-destination Alloy app cannot be cleanly produced by a cluster-generator ApplicationSet selecting the SPOKE secret — this exact failure mode was already analyzed and the cluster generator REJECTED in auto-008.
- ADR claim: "The hub-destination alloy agent keeps `destination` = in-cluster hub but templates its spoke-derived URLs from the same generator." (lines 63-64), and folds the alloy app into the ApplicationSet design.
- Evidence: the cluster generator emits one Application per matched cluster with generator params (`.name`, `.server`, metadata) bound to the SELECTED (spoke) cluster. To keep `destination.server: https://kubernetes.default.svc` (the hub — `observability-alloy-mgmt.yaml:48-50`) while iterating the spoke secret, the template must HARD-CODE the hub server and ignore `{{.server}}`. That is exactly the "risks accidentally targeting the hub in-cluster destination" hazard that auto-008 cites to reject the cluster generator for phase 3 (`decisions/auto-008-spoke-gitops-delivery.md:125-128`, reviewer F1). The ADR does not mention auto-008 having already considered and rejected this generator on this exact ground.
- Project mismatch compounds it: alloy uses `project: hub-addons` (`observability-alloy-mgmt.yaml:33`) which permits ONLY destination `https://kubernetes.default.svc` namespace `monitoring-agent` (`hub-addons.yaml:46-48`). The other apps use `platform-spoke`, whose destinations are `platform-spoke`/`*-spoke` by NAME and EXPLICITLY forbid the hub server (`platform-spoke.yaml:56-61`). A single ApplicationSet template cannot emit both an `hub-addons`/hub-server Application AND `platform-spoke`/by-name Applications — the `project` and `destination` fields differ structurally. So alloy CANNOT "fold into the same ApplicationSets"; it needs its own AppSet (or stays a plain Application). The ADR's "collapse into the same ApplicationSets" (lines 61-64) is mechanically wrong.
- Fix: keep alloy as a separate ApplicationSet (or a plain Application) with project hub-addons and a hard-coded hub destination; explicitly reverse auto-008's F1 rejection with new rationale.

## MAJOR

### M1. ADR says "nine spoke Applications"; the tree has TEN files under argocd/apps/spoke/ (one is the HUB alloy app). The count and the "9 → ApplicationSets" mapping are off, and several apps share NO common fact set, so they cannot collapse into one ApplicationSet.
- Evidence: `ls argocd/apps/spoke/` = 10 files: external-dns, hello, ingress-nginx, keycloak, observability-alloy-mgmt (HUB), observability-kube-prometheus-stack, observability-loki, workload1-external-dns, workload1-hello, workload1-ingress-nginx. The ADR repeatedly says "nine per-app Applications" (lines 13, 54). If alloy is excluded that's 9 SPOKE apps, but then the ADR ALSO says alloy folds into the AppSets (line 63) — inconsistent. Either way the workload1-* files (lines 50-34 in their headers say "Phase 6") are duplicates-by-cluster of the platform ones, so an honest cluster-generator design produces a SINGLE AppSet per add-on fanning across both spoke secrets — not "nine ApplicationSets." The ADR conflates "one AppSet per add-on, two generated apps" with "nine apps replaced by ApplicationSets."
- Fix: state the real shape — N add-ons → N ApplicationSets, each generating one Application per matching spoke secret; reconcile the 9-vs-10 count and the alloy exception.

### M2. Sync-wave ordering across spokes is NOT preserved by putting waves on generated Applications — and the bootstrap relies on a non-existent `SyncWaves=true` syncOption, so the wave story is doubly shaky.
- ADR claim: "Is sync-wave ordering preserved when waves are annotations on generated Applications?" — the ADR asserts ordering is kept (PR #210 chain, lines 60, 110-111).
- Evidence: (a) Today waves (e.g. ingress-nginx `:26` wave 20, hello `:15` wave 30, keycloak `:31` wave 40) order the CHILD Applications inside the BOOTSTRAP app's sync. Once these become AppSet-generated Applications, they are still ordered relative to each other within bootstrap's reconcile only if the AppSet propagates the `argocd.argoproj.io/sync-wave` annotation onto the generated Application metadata — the ADR does not specify that the template sets it, and the cluster-generator template must explicitly carry `metadata.annotations`. (b) More fundamentally, `bootstrap.yaml:55` lists `- SyncWaves=true` as a syncOption. There is NO such ArgoCD syncOption — sync waves are always-on and not toggled by a `SyncWaves` option (the real knob is `ApplyOutOfSyncOnly` / waves are implicit). This is a pre-existing fiction in bootstrap.yaml that the ADR leans on ("SyncWaves option enforces that," bootstrap comment lines 53-55). The ADR should not cite wave ordering as a preserved guarantee without fixing this.
- Fix: require the AppSet template to copy the sync-wave annotation onto generated Applications; separately, correct/remove the bogus `SyncWaves=true` option claim.

### M3. argo-cd chart pin is 6.7.3 (ArgoCD ~v2.10), but the kubeconform CRD store is pinned to argo-cd v2.13.1 — a version skew. The ADR asserts the pinned chart's ApplicationSet CRD supports goTemplate + the cluster generator without verifying against 6.7.3.
- Evidence: `terraform/management/variables.tf:72-75` → `argocd_version` default `"6.7.3"` (the argo-cd HELM chart version, which maps to ArgoCD app ~v2.10.x, NOT v2.13). `scripts/fetch-crds-for-kubeconform.sh:136-137` pins the Application/AppProject CRDs to `argo-cd/v2.13.1`. So even the existing Application schema in the store is from a DIFFERENT ArgoCD version than what is deployed; an ApplicationSet schema pulled from v2.13.1 would validate against features the deployed 2.10 controller may not support.
- On the substance: ApplicationSet controller IS bundled and enabled by default in argo-cd chart 6.x (true), and goTemplate + the cluster generator exposing secret labels/annotations via `{{index .metadata.annotations ...}}` are supported from ArgoCD ~2.6+, so 2.10 is functionally fine. But the ADR states this as fact (line 106 "ships enabled in the pinned argo-cd chart") without naming 6.7.3 or noting the goTemplate metadata-access path requires `goTemplateOptions: ["missingkey=error"]` discipline to fail loudly. The version-skew between deployed chart and CRD store should be flagged.
- Fix: name the pin (6.7.3 → ArgoCD 2.10.x) in the ADR; align the kubeconform CRD pin to the deployed ArgoCD minor; confirm goTemplate cluster-generator metadata access on 2.10.

## MINOR

### m4. Five unit test files break or need changes — the ADR only names test_spoke_apps.sh "and peers" (line 108), which understates it. Specifics:
- `tests/unit/test_spoke_apps.sh`: loops `for app in SPOKE_DIR/*.yaml` and HARD-asserts `kind == Application` (line 25, `continue` on mismatch). An ApplicationSet file → `FAIL`. Also asserts `.spec.destination.name`/`.spec.project` at top level (lines 27-54) which live under `.spec.template.spec` in an AppSet. Also `hub_count` logic (lines 43, 87-88) expects exactly one `Application` with project hub-addons — broken if alloy becomes an AppSet. Needs a full rewrite for kind ApplicationSet + `.spec.template.spec.*` paths.
- `tests/unit/test_observability_apps.sh`: §1 asserts `.kind == Application`, `.spec.project`, `.spec.destination.name`, `.spec.sources|length==2` at top level (lines 41-57); §3 asserts the alloy app is `kind Application` with top-level `.spec.destination.server` (lines 178-198). All these paths move under `.spec.template.spec` for AppSets. Breaks.
- `tests/unit/test_keycloak_apps.sh`: asserts `.kind==Application`, top-level `.spec.project`/`.spec.destination.name`/`.spec.sources[]` (lines 39-86). Breaks.
- `tests/unit/test_workload1_apps.sh`: loops `workload1-*.yaml` asserting top-level Application fields + `.spec.source.helm.valuesObject.subdomain` (lines 39-97); if workload1 apps collapse into shared AppSets the FILES DISAPPEAR and `found` stays 0 → `FAIL: no workload1-* spoke apps found` (line 79). Breaks hard.
- `tests/unit/test_argocd_app_revision_pinned.sh`: globs `argocd/apps/*.yaml` NON-recursively (line 21) and skips non-`Application` kinds (line 27 `continue`). It does NOT scan `apps/spoke/`, so it is unaffected by the spoke change — but if any AppSet is placed directly in `argocd/apps/` it would be silently skipped (revision NOT checked). Note, don't "fix."
- `tests/unit/test_platform_spoke_appproject.sh` / `test_hub_addons_appproject.sh`: do NOT break (they only read the AppProject files, which are unchanged). The ADR is right to leave them; worth stating explicitly.

### m5. AppProjects do not restrict the ApplicationSet KIND, but the generated Applications' resource whitelists are unchanged — verify the generated apps still pass project scoping.
- Evidence: bootstrap recurses `argocd/` and applies AppProjects + (new) ApplicationSets. ApplicationSet objects are created in the `argocd` namespace under bootstrap's `default` project; the `default` project has no kind restriction, so AppSet creation is not blocked. The GENERATED Applications still carry `project: platform-spoke`/`hub-addons`, and the existing `clusterResourceWhitelist`/`namespaceResourceWhitelist` (platform-spoke.yaml:64-104, hub-addons.yaml:52-74) are unchanged — so generated apps remain within scope IFF the template sets the same `project` as today. This is fine but UNSTATED; the ADR should assert the template's `spec.template.spec.project` equals the current per-app project, and add a lint that the AppSet template project matches.

### m6. The cluster-generator selects on label `k8-platform.io/cluster-role: spoke`, but the per-app destination today is by NAME (`platform-spoke`, `workload1-spoke`). The generated Application's destination must be `{{.name}}` from the secret — the ADR's `short-name`-based NAMING claim conflates Application NAME with destination cluster NAME.
- Evidence: spoke apps use `destination.name: platform-spoke` / `workload1-spoke` (hello.yaml:27, workload1-hello.yaml:33), which is the ArgoCD cluster Secret NAME (auto-008:146-150). The ADR proposes deriving the generated Application's NAME from a `k8-platform.io/short-name` label (lines 49, 58-60) but the DESTINATION must come from the cluster secret's `name` (the generator's `{{.name}}`). These are two different identifiers; the ADR text mixes them ("preserve today's names via the short-name label"). PR #210's live check keys on the Application name `spoke-hello`, so the template must set `metadata.name: {{index .metadata.labels "k8-platform.io/short-name"}}-hello` AND `destination.name: {{.name}}`. Worth disentangling explicitly.
