# Skill: `tell-me-about-this-repo`

Implements [`lago-morph/idea-pipeline#16`](https://github.com/lago-morph/idea-pipeline/issues/16) plus the orchestration rules established in this repo's PRs #12 and #13.

## Hard rules

1. **Both report-generation operations are ALWAYS done in a subagent**, never inline. The orchestrator's job is routing, dispatch, render-check, and (when applicable) the consistency loop — not writing the doc itself.
2. **The subagent runs in an isolated worktree** (`isolation: "worktree"` on the `Agent` call). This is true whether one or both reports are being generated.
3. **The filename embeds the short commit hash.** Different hash → different file → never overwrite. Pattern:
   ```
   summary/{functionality|status}-YYYY-MM-DD-{short-hash}.md
   summary/run-log-YYYY-MM-DD-{short-hash}.md
   ```
4. **Render-verify every Mermaid diagram before declaring done.** Literal `|` inside node-label brackets breaks GitHub rendering. The check is one `awk | grep` command (Step 4 below).

## Routing

Classify the user's intent before dispatching:

| User intent | `MODE` | Dispatch |
|---|---|---|
| Generic — "summary of this repo", "tell me about this repo" | `both` | Two subagents in parallel, one per kind |
| Functionality-only — "what does this repo do", "what is this repo" | `functionality_only` | One subagent (functionality) |
| Status-only — "where are we", "what's left", "project status" | `status_only` | One subagent (status) |

If the phrasing is ambiguous between two interpretations, ask once via `AskUserQuestion`. Do not guess.

## Workflow

### Step 1 — Verify date and capture commit hash

```bash
UTC_DATE=$(date -u +%Y-%m-%d)
HASH=$(git rev-parse --short HEAD)
```

Cross-check the date with a second tool (`python3 -c "import datetime; print(datetime.datetime.now(datetime.UTC).strftime('%Y-%m-%d'))"`). Both must agree.

### Step 2 — Detect pre-existing same-hash artifacts

```bash
FUNC_EXISTING=$(ls summary/functionality-*-${HASH}.md 2>/dev/null | head -1)
STATUS_EXISTING=$(ls summary/status-*-${HASH}.md 2>/dev/null | head -1)
```

This decides whether the consistency review loop (Step 5) will need to run.

### Step 3 — Dispatch subagents

When dispatching **both** subagents, send them in a **single message with two `Agent` tool calls** so they run in parallel. Each subagent's brief MUST include:

- `UTC_DATE` and `HASH`.
- For functionality: read `resources/generate-functionality.md` (full instructions).
- For status: read `resources/generate-status.md` (full instructions).
- `isolation: "worktree"`.
- `subagent_type: "general-purpose"`.
- A 5-line report-back contract (path, line count, diagram count, brief summary).

When subagents return, copy their produced files from their worktrees into the orchestrator's `summary/`.

### Step 4 — Render-verification preflight

```bash
awk '/^```mermaid/,/^```$/' summary/functionality-${UTC_DATE}-${HASH}.md summary/status-${UTC_DATE}-${HASH}.md 2>/dev/null \
  | grep -nE '\[[^][]*\|[^][]*\]'
```

If anything matches, fix it (replace `|` with `/` or `&#124;` inside the offending node label) before proceeding. The subagents are instructed to do this themselves; this is the orchestrator's safety net.

### Step 5 — Consistency review loop (conditional)

Run the loop **if and only if both files exist for `${HASH}` after Step 3**:

- `MODE=both` → always run.
- `MODE=functionality_only` AND `STATUS_EXISTING` was non-empty → run.
- `MODE=status_only` AND `FUNC_EXISTING` was non-empty → run.
- Otherwise → skip. Append a one-line note to the run-log explaining why.

**Procedure is in [`resources/review-loop.md`](resources/review-loop.md).** Load that file when (and only when) the loop is going to run.

### Step 6 — Commit, push, PR

- Use a feature branch (e.g. `docs/summary-${UTC_DATE}-${HASH}`); never commit to `main`.
- Push: `git push -u origin <branch>`.
- Open a PR. Default `draft: true`. Set `draft: false` only if the user explicitly requested a finalized PR.
- PR body lists the three files (functionality, status, run-log) and embeds a one-paragraph summary.

## Outputs

- `summary/functionality-{UTC_DATE}-{HASH}.md` (created/edited; subagent-generated).
- `summary/status-{UTC_DATE}-{HASH}.md` (created/edited; subagent-generated).
- `summary/run-log-{UTC_DATE}-{HASH}.md` (created/appended; orchestrator-written when the review loop runs).

## Progressive disclosure — when to load what

The top-level file you are reading covers the common path: routing, dispatch, filename convention, render preflight. Load deeper files only when needed:

- **About to dispatch a functionality subagent?** Pass it `resources/generate-functionality.md` in its brief — that's all it needs.
- **About to dispatch a status subagent?** Pass it `resources/generate-status.md`.
- **About to run the consistency review loop?** Read `resources/review-loop.md` yourself; it contains the per-round procedure, the reviewer-brief template, and the termination rules. Do NOT read it on every invocation — only when Step 5 actually triggers.

## Anti-patterns

- **Generating the doc in the orchestrator's own context.** Always dispatch a subagent.
- **Sharing a worktree across the two subagents.** Use `isolation: "worktree"` on each.
- **Overwriting a summary file that has a different hash in its name.** Different hash = different artifact. Write a new file.
- **Skipping the render-verification preflight.** PR #13 in this repo's history is the entire reason this step exists.
- **Dispatching sub-agents serially when both are wanted.** One message, two `Agent` calls.
- **Reading `resources/review-loop.md` on every invocation.** It's only loaded when Step 5 triggers (both files exist for the same hash).
