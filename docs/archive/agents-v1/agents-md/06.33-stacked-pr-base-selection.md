# 6.33 Base a stacked PR on the branch carrying the files it edits

**Rule.** When you open a stacked PR that edits a file, set its base to the branch
that already holds the **most recent version** of that file — not `main`, and not an
older sibling branch lower in the stack. Pick the base by asking: *which open branch
last touched the files I am about to edit?* Base on that one.

## Why this matters

Git switches the working tree to match the branch you check out. If you create a new
branch off a parent that has an **older** copy of a file than another open branch
does, then checking out your new branch silently restores that older copy. The
working tree looks clean — `git status` shows nothing unusual — so the regression is
invisible until someone diffs against the branch that actually had the newer content.
A reflexive `git add -A && git commit` at that point ships the reverted file onto the
stack as if it were intended work.

## How to choose the base

1. Identify every file the new PR will edit.
2. For each, find the open branch that most recently modified it
   (`git log --oneline -1 -- <path>` across the candidate branches, or recall which
   open PR last touched it).
3. Base the new branch on the branch that is **highest in the stack among those that
   touch your files** — that branch transitively contains the others' versions too.
4. If two independent branches both edit the same file and neither descends from the
   other, they are not safely stackable on each other; rebase one onto the other
   first, or fold them together.

## Recovery if you got it wrong

If a harness reminder (or a diff) shows your committed edits appearing as "reverted"
in the working tree, you almost certainly based on the wrong parent. Do **not**
commit. Recreate the branch off the correct parent
(`git checkout <correct-parent> && git checkout -b <branch>`), or `git checkout
HEAD -- <path>` to discard the spurious working-tree reverts before continuing.

*Grounded in: 2026-06-07 (retrospective 2026-06-07-181, `AGENTS-MD-3b7577c63e`) — the
sandbox-kubectl feasibility branch was first based on the run-summary branch, but the
`AGENTS.md` and `autonomous-run` edits it needed lived on the human-readable branch
one level up; checking the new branch out showed those edits as reverted until it was
re-based onto the correct parent.*
