# 6.12 Don't claim a tool is "unavailable" until you've tried to install or start it

**Before reporting "X is not available in this sandbox" or deferring
work on that basis, attempt the obvious installation or activation
paths:**

1. **Already installed but not at PATH?** `which X`, `ls /usr/bin/X
   /usr/local/bin/X /root/.local/bin/X`.
2. **Daemon installed but stopped?** `systemctl status X`, `service X
   status`, `pgrep X`, `sudo Xd &`.
3. **One-line install available?** `curl -fL <release-url> -o /tmp/X
   && chmod +x /tmp/X`.

Report "unavailable" only after at least one of those attempts has
failed with a concrete error. The wrong shape of "unavailable" claim
is `which X` returning nothing — that's an unanswered question, not
an answer.

**Known-good in THIS sandbox (do not re-derive; do not call them absent):**

- **Docker** is installed but stopped — start it with `sudo dockerd &`
  (needed by `scripts/composition-render.sh`).
- **kubectl** reaches the live clusters through the SSM relay. Install the
  CLI (`scripts/sandbox-setup.sh` does it, pinned `KUBECTL_VERSION`) plus
  `session-manager-plugin`, then read any cluster with
  `scripts/sandbox-kubeconfig.sh -c <cluster> --exec kubectl ...` (read-only;
  see the [`sandbox-kubectl-access`](../skills/sandbox-kubectl-access/SKILL.md)
  skill and `docs/decisions/0008`). Direct kubectl 503s — that is the relay's
  job, not a missing tool.

Both are installed/started automatically by `scripts/sandbox-setup.sh`, which
the SessionStart hook runs. If a session ever finds them missing, run that
script before declaring anything unavailable.

sandbox") that turned out to be wrong on both counts — docker daemon
