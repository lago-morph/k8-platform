# 6.30 Ground architectural framings in real repo artifacts, not invented distinctions

**Ground architectural framings in real repo artifacts, not invented
distinctions.** Do not introduce an architectural distinction or named mechanism
that has no referent in the actual repo; verify the artifact exists (the
workflow, the script, the field) before building a plan on it, because a phantom
distinction survives until an adversary greps for it.

*Grounded in: 2026-06-07 — the plan's "build ≠ CI" split had no referent (there
is no bring-up script; `apply-and-verify` IS a workflow_dispatch job); three
round-3 reviewers independently grepped and collapsed it.*

## Justification

The synthesized plan built its whole execution model on a "build (not CI)"
context, as if a separate build executor existed that ran verification outside
GitHub Actions. It did not: `grep` finds no `apply-and-verify.sh` /
`bring-up.sh` / `verify-platform.sh`; the bring-up *is* the
`action=apply-and-verify` input of a `workflow_dispatch` job in
`terraform-test.yml`. The distinction was a comfortable abstraction with no
ground truth, and it distorted the entire "on by default" story until three
round-3 reviewers independently grepped the tree and collapsed it to the real
two-surface model. One `ls scripts/` at framing time would have prevented a
revision pass. When a plan leans on "the X step" or "the Y mechanism," confirm X
and Y exist in the repo before everything downstream inherits the fiction.
